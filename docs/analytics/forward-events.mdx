---
title: Send Restage events to your analytics tool
description: Forward surface events to Firebase Analytics, PostHog, Mixpanel, Amplitude, Segment or OpenTelemetry, and connect them to app activation and retention.
---

Subscribe to `Restage.events` to send surface activity to the analytics SDK already in
your app. Each event has a stable `name` and a flat `analyticsProperties` map. The same
subscription works for paywalls, onboarding, messages, surveys and general surfaces.

The examples below use the upcoming SDK API. You need the Restage release that introduces
`analyticsProperties`, or a later one.

## Connect your analytics SDK

Initialize Restage and your analytics SDK before you mount a surface. Subscribe once and
keep the returned subscription. Call `await subscription.cancel()` when the code that owns
it shuts down.

Subscribe before you show a surface. The stream broadcasts new events and doesn't replay
earlier ones.

All examples also import `package:restage/restage.dart`, and assume the vendor SDK is
already configured for your project. The vendor SDK controls its own identity, consent
settings, batching and delivery. Restage event properties contain no installation or
account identifier. The vendor attaches its own current user to the forwarded event.

### Firebase Analytics

Add `firebase_analytics` and import
`package:firebase_analytics/firebase_analytics.dart`. Set up Firebase with the
[Firebase setup guide](https://firebase.google.com/docs/analytics/flutter/get-started).

```dart
final subscription = Restage.events.listen((event) {
  FirebaseAnalytics.instance.logEvent(
    name: event.name, parameters: event.analyticsProperties,
  );
});
```

[DebugView](https://firebase.google.com/docs/analytics/debugview) shows incoming events
and their parameters. To use a parameter in reports, including `restage_experiment` and `restage_variant`, register it as a custom dimension. Firebase's
[event guide](https://firebase.google.com/docs/analytics/flutter/events) covers the
setup.

### PostHog

Add `posthog_flutter` and import `package:posthog_flutter/posthog_flutter.dart`.
Initialize it with your project's token and region, as in the
[PostHog Flutter guide](https://posthog.com/docs/libraries/flutter).

```dart
final subscription = Restage.events.listen((event) {
  Posthog().capture(
    eventName: event.name, properties: event.analyticsProperties,
  );
});
```

### Mixpanel

Add `mixpanel_flutter` and import `package:mixpanel_flutter/mixpanel_flutter.dart`.
`mixpanel` below is the instance returned by `await Mixpanel.init(...)`. See the
[official Flutter library](https://mixpanel.github.io/mixpanel-flutter/packages/mixpanel_flutter/).

```dart
final subscription = Restage.events.listen((event) {
  mixpanel.track(
    event.name, properties: event.analyticsProperties,
  );
});
```

### Amplitude

Add `amplitude_flutter` and import `package:amplitude_flutter/amplitude.dart`
and `package:amplitude_flutter/events/base_event.dart`. `amplitude` below is your
initialized SDK 4 instance. See the
[Amplitude Flutter guide](https://www.amplitude.com/docs/sdks/analytics/flutter/flutter-sdk-4).

```dart
final subscription = Restage.events.listen((event) {
  amplitude.track(BaseEvent(
    event.name, eventProperties: event.analyticsProperties,
  ));
});
```

### Segment

Add `segment_analytics` and import `package:segment_analytics/client.dart`.
`analytics` below is your configured client, created with
`createClient(Configuration(writeKey))`. Import `Configuration` from
`package:segment_analytics/state.dart`. See the
[Segment Flutter guide](https://www.twilio.com/docs/segment/connections/sources/catalog/libraries/mobile/flutter).

```dart
final subscription = Restage.events.listen((event) {
  analytics.track(
    event.name, properties: event.analyticsProperties,
  );
});
```

### OpenTelemetry

Add `dartastic_opentelemetry` and import
`package:dartastic_opentelemetry/dartastic_opentelemetry.dart`. Initialize
`OTel` with your app's exporter before you subscribe (see the
[Dartastic logs guide](https://pub.dev/packages/dartastic_opentelemetry#logs)). Then get
a logger with `final logger = OTel.logger('restage');`.

```dart
final subscription = Restage.events.listen((event) {
  logger.emit(
    eventName: event.name,
    attributes: OTel.attributesFromMap(event.analyticsProperties),
  );
});
```

Each surface event becomes a named log record with the same properties as the other
integrations. Your existing exporter sends it to your collector.

To check delivery locally, initialize with `logRecordExporter: ConsoleLogRecordExporter()`
and call `await OTel.loggerProvider().forceFlush()` after you dismiss the surface. The
console should show `paywall_dismissed` and its `restage_variant` attribute.

## Read the served assignment

Once a surface has painted, you can read its assignment synchronously:

```dart
final assignment = Restage.assignmentFor(
  'pro_upgrade', surfaceType: Surface.paywall,
);
final useTreatment = assignment?.experimentId == 'upgrade_v2' &&
    assignment?.variantId == 'treatment';
```

Replace the example values with your experiment and arm IDs. `variantId` is the served arm's canonical ID and can differ from the arm's display label. The result also has `experimentRevisionId` and `experimentEpochId` for telling revisions and successive runs apart.

A resolver result has its own assignment. The global accessor changes only after a successful presentation, and it makes no network request and evaluates no assignment.

For a surface delivered through a placement, the accessor and surface events use the
surface experiment's assignment when there is one. Otherwise they use the placement
experiment's assignment. When both experiments apply, this lookup returns the surface
experiment. The delivery decision path keeps both assignments. A joint selection without
an individual experiment arm has no single assignment.

### What the accessor returns

The accessor keeps the last successfully presented assignment after the surface is dismissed. It changes or clears like this:

- A hosted replacement that painted successfully updates it. A hosted screen built offstage doesn't.
- A bundled fallback has no experiment assignment.
- A paywall fallback clears the previous assignment when it paints.
- Your compiled screen or flow as the fallback makes the lookup return null until a later confirmed presentation, even when the fallback is offstage. Those native roots can't always report paint. The SDK stops claiming the previous assignment.
- Failed loads, prefetched candidates and abandoned refreshes don't replace the served assignment.
- `Restage.reset()` clears the lookup for the previous actor.

The lookup lives in the current process. It doesn't keep a cohort across app restarts.

If several instances of the same surface are active, the accessor returns null. It won't pick one. To tie behavior to one instance, use that instance's event `assignment`. Every event keeps its own attribution snapshot, even if you read it after another surface has rendered. Events fired after an identity reset don't inherit the previous actor's assignment.

## Connect exposure, activation and day-7 retention in PostHog

Say `pro_upgrade` has a treatment arm that changes whether an app feature is free.
Forward the surface stream with the PostHog snippet above. When your app's activation
milestone happens, tag that event with the assignment your app actually used:

```dart
final assignment = Restage.assignmentFor(
  'pro_upgrade', surfaceType: Surface.paywall,
);
await Posthog().capture(
  eventName: 'app_activated',
  properties: {
    if (assignment != null) ...{
      'restage_experiment': assignment.experimentId,
      'restage_experiment_epoch': assignment.experimentEpochId,
      'restage_variant': assignment.variantId,
    },
  },
);
```

Send `app_active` from your app when a user comes back and does what your product counts
as a return. Use the same PostHog identity across these events. The cohort example needs
identified PostHog events and person profiles. Configure those in your app's existing
PostHog integration. Restage sends no activation or retention event for your app.

Build a [PostHog funnel](https://posthog.com/docs/product-analytics/funnels) with the
steps `paywall_viewed` then `app_activated`:

- Filter the first step by `restage_surface_id=pro_upgrade` and the experiment ID and
  epoch.
- Break down by `restage_variant`, attributed to the first step.
- Choose a conversion window that matches your activation definition.

This shows how many users who saw each arm activated.

For retention, save the treatment arm's converted users as a
[cohort](https://posthog.com/docs/data/cohorts). Then create a
[retention insight](https://posthog.com/docs/product-analytics/retention) filtered to
that cohort:

- Start event `app_activated`, return event `app_active`.
- Daily intervals and first-time retention.
- Returning criteria **On**.

Read Day 7 after that interval has completed, and repeat for the control cohort. A static cohort captures the users in the selected funnel window. Refresh it when you look at a new window.

Together these answer "saw paywall B, activated, then returned on day 7 after
activation." A seven-day funnel window alone measures conversion within seven days.

To break retention down by event properties, put the original cohort's variant on both
the start and return events. PostHog needs matching breakdown values. Keep that cohort in
your app or analytics tool across restarts. The served accessor lives in the current
process. It only reflects the current run of your app.

## Property format

Besides lifecycle events, admitted Measurement points produce `surface_point_presented` and `surface_point_interacted`. Both carry `restage_occurrence_id` and `restage_lineage_id`, plus the same surface attribution.

- Point events arrive asynchronously, after the measurement worker accepts them.
- A presented point means the point was first retained as a member of that surface session. Several points can belong to one screen. Use `paywall_viewed` for the root-view funnel above.
- An interaction reports activity. It doesn't prove a purchase, activation or other outcome by itself.

`FlowDismissed` (`flow_dismissed`) means an active, rendered general flow was removed before it completed or was skipped. It says nothing about the user's intent. Unpainted candidates and refresh cleanup don't emit it.

If your app switches exhaustively on the sealed `RestageEvent` type, add cases for `SurfacePointPresented`, `SurfacePointInteracted` and `FlowDismissed` when you upgrade.

`analyticsProperties` holds SDK-defined fields meant for automatic forwarding. Every name starts with `restage_`, including details such as `restage_reason` and `restage_time_on_surface_ms`. It leaves out custom-event arguments, survey answers, diagnostic messages, host context and opaque measurement capabilities. Your local typed event callbacks still have them.

The map follows [Firebase's parameter limits](https://firebase.google.com/docs/reference/android/com/google/firebase/analytics/FirebaseAnalytics.Param):

- At most 25 entries.
- Parameter names of at most 40 characters.
- String values of at most 100 characters.

SDK event and parameter names use snake_case, start with a letter and avoid reserved prefixes. Values are strings or finite numbers. Booleans become `1` or `0`, and absent values are omitted. Keep any properties you add yourself within your vendor's limits too.

The surface fields are `restage_surface_id`, `restage_surface_type` and `restage_surface_version`. Assigned events add `restage_experiment`, `restage_experiment_revision`, `restage_experiment_epoch` and `restage_variant`. Events fired before a served version exists leave out that version and assignment.

String values are cut to at most 100 UTF-16 code units, at a Unicode character boundary. The typed event and the assignment accessor keep the complete identifiers. Use short, distinct IDs when you compare them in a vendor report. If you add the raw assignment fields to app events as above, keep those IDs within your vendor's limits too.

## Verify delivery

Show a surface, dismiss it, and look for `paywall_dismissed` in your vendor's event
viewer. For an experiment's treatment arm, check `restage_variant=treatment` next to the
expected surface, version and experiment fields. If your arm ID isn't `treatment`, use
the one configured in your experiment.

On Android, turn on Firebase DebugView for your app's package before the run:

```sh
adb shell setprop debug.firebase.analytics.app com.example.app
```

Open Firebase Analytics DebugView, choose the device, select the event and check its
parameters. In PostHog, find the same event in your project's activity view. When you're
done, turn Firebase debug mode off:

```sh
adb shell setprop debug.firebase.analytics.app .none.
```

An event in `Restage.events` only proves the SDK emitted it locally. To check the vendor
configuration and network delivery, confirm it arrived in the vendor project.
