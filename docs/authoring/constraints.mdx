---
title: Authoring constraints
description: The Flutter source the build can compile into a surface, and what to write when it can't.
---

A surface is built from your Flutter source, so the build has to be able to follow
your code. Most of what you already write works as it is. This page lists the rules
that do apply, with what to write instead. When the build can't follow something, it
stops with an error that points at the line, before anything can be published.

The rules are the same for every surface: onboarding, messages, surveys, paywalls, and
any screen.

## Locals before the return

`build` may start with `final` and `const` local variables, one per statement, and end
with one returned widget. Locals can read the theme, refer to each other, or hold a
widget, including one of your own custom widgets. The result is the same as if you had
written each value inline:

```dart
@override
Widget build(BuildContext context) {
  final scheme = Theme.of(context).colorScheme;
  final title = Text('Go Pro', style: TextStyle(color: scheme.primary));
  return Column(children: [title, const Text('Everything, one plan.')]);
}
```

The returned widget has to use every local, directly or through another local. A local
it doesn't use stops the build with the local's name, because its value would never
reach the surface; a call such as `final pushed = Navigator.push(...)` would otherwise
disappear without a trace. Several variables in one statement (`final a = 1, b = 2;`),
`late`, a `final` with no value, and any statement other than a local or the return
also stop the build. See [Theming](/authoring/theming) for how theme reads through a
local stay live.

## Helper methods

A method of your own that returns a widget or a value is followed and inlined where you
call it, with its arguments:

```dart
Widget _plan(String name, String price) =>
    ListTile(title: Text(name), trailing: Text(price));

@override
Widget build(BuildContext context) => Column(
      children: [_plan('Monthly', '\$4.99'), _plan('Annual', '\$39.99')],
    );
```

This works for methods in the same class and for top-level or static functions anywhere
in your package, such as `Spacing.page()` or `PlanBadge.pro()`, and in dependency
packages that publish custom Restage widgets. See
[Design-system packages](/authoring/design-system-packages). Other package calls
stop the build with an error that names them. The helper's body is one returned
expression, optionally after `final` locals. Pass every optional parameter explicitly,
and a helper can't call itself. For a component you reuse across surfaces, extract a
[custom widget](/authoring/custom-widgets).

## Your own widget classes

A widget you move into its own class needs `@RestageWidget`. A class the build doesn't
know stops the build with an error that says so. With the annotation, the build
compiles a widget that only composes other widgets into the surface, and registers the
others so your app renders them from its own compiled code. See
[Custom widgets](/authoring/custom-widgets).

## Constants

A top-level or `static const` declared in the same file works anywhere a value goes,
whether it's a number or string or a value such as a `Color`, `EdgeInsets`,
`TextStyle`, `BorderRadius`, or `Alignment`:

```dart
const kBrand = Color(0xFF6E5AFF);
const kPagePadding = EdgeInsets.all(20);

// later, in build():
Container(padding: kPagePadding, color: kBrand)
```

A constant declared in another file or package works the same way. Its value goes into
the delivered surface, so editing the constant and pushing updates the surface on
installed apps. Enum values work.

### Reserved class names

Avoid the following names for your own classes in authored surface code. The build
reserves them for framework values and constants:

| Kind | Names |
| --- | --- |
| Constant namespaces | `Colors`, `Icons`, `CupertinoIcons` |
| Named constant values | `FontWeight`, `TextDecoration`, `Curves` |
| Structured values | `Alignment`, `AlignmentDirectional`, `AssetImage`, `Border`, `BorderRadius`, `BorderRadiusDirectional`, `BorderSide`, `BoxDecoration`, `BoxShadow`, `Color`, `DecorationImage`, `EdgeInsets`, `EdgeInsetsDirectional`, `IconThemeData`, `LinearGradient`, `Locale`, `NetworkImage`, `Offset`, `Paint`, `RadialGradient`, `Radius`, `Size`, `SweepGradient`, `SystemUiOverlayStyle`, `TextStyle` |
| Numeric constants | `double` |

A static constant on an application class with one of these names is rejected,
even if its value could otherwise be substituted. Rename the class, or inline the
value at the use site, as the diagnostic suggests. Ordinary framework uses such as
`Colors.blue` and `EdgeInsets.zero` still work.

## Lists written in the source

A `for` over a list literal or a same-file `const` list, a collection `if` on a
condition the build can work out, and a spread of a list literal all expand at build
time, nested as deep as you like:

```dart
const kFeatures = ['Unlimited projects', 'Priority support', 'Export'];

Column(
  children: [
    for (final feature in kFeatures) Text(feature),
    if (showFootnote) const Text('Cancel any time.'),
    ...const [Divider(), SizedBox(height: 8)],
  ],
)
```

A `for` over a value that is only known when the app runs, such as a constructor
parameter, is [host data](/authoring/host-data) and stays a loop in the surface. Not
supported: a C-style `for`, a null-aware spread (`...?`), sets and maps, `.map()`
chains, and a condition on a build-mode constant such as
`kDebugMode`. One list can expand to at most 1,000 children. Callbacks inside a static `for`
are compiled for each iteration, including event arguments from the loop variable.
`TextSpan.children` requires a static list: spread, collection `if`, and collection
`for` elements are not supported there.

## Builder callbacks

`LayoutBuilder`, `OrientationBuilder`, native GridView item/delegate callbacks, and
supported SVG placeholders accept pure typed callbacks. Use expression bodies or
blocks with immutable locals and conditional returns. Captured data, typed member
and index reads, arithmetic, string interpolation, and supported helpers keep their
Dart evaluation order. Boolean operators, conditional expressions, and null
coalescing evaluate only the selected branch.

Constraints, orientation, and supported inherited reads come from the native
callback's local context. Guard unbounded constraints before using them as finite
layout values. A nullable item builder can return null without evaluating later
index reads. Scalar `ValueKey` values belong on returned widget roots; opaque
object keys and unsupported descendant keys are diagnosed.

Supported callback-local `Theme` and `DefaultTextStyle` paint values retain native
color components/color space, font weights from 1 through 1000, and combined text
decorations in native Flutter paint properties. Inside builders, custom catalog
arguments require proven base `Color` and `FontWeight` values, including inside
`TextStyle`, gradients, and shadows. Examples include `Colors.black`, `Color(...)`,
`FontWeight.bold`, and `FontWeight(550)`. Deferred colors/font weights and subtypes
such as `Colors.red` (`MaterialColor`) are diagnosed, even through a `Color`-typed
alias. Ordinary Flutter paint properties keep their existing color admission.
The optional SVG theme/filter slots also require proven base colors outside
callbacks; see [Optional SVG](/authoring/widget-catalog#optional-svg).
Arbitrary host Color captures and equality comparisons between Color objects are
outside the callback subset; null checks are allowed.

Mutation, async/generators, recursive helpers, custom operators/getters, and arbitrary
application calls cannot be delivered through these callbacks. A source diagnostic
names the unsupported expression. Explicit controller objects and imperative
delegates belong in installed application code.

## Events on callbacks

Pass `surfaceEvent(...)` directly as the callback, for taps and value callbacks alike:

```dart
onPressed: surfaceEvent(next),
onChanged: surfaceEvent(pick),
```

When the widget passes a value, such as a Switch's `bool` or a TextField's text, that
value is the event's value. Don't wrap the call in a closure: `() => surfaceEvent(next)`
returns the callback without calling it, so the event never fires when your own widget
shows as the fallback. The build compiles it with a warning.

A possibly missing nullable value read inside a builder needs a matching non-null
guard or a fallback covering every null/missing case before it can enter an event
payload, even if the event type permits null. Otherwise the build diagnoses that
payload. Native callbacks that already deliver nullable event values keep their
existing behavior.

## Build text from parts

An interpolated value can be any non-null `String` the surface can read: host data, a
`State` field, a `final` local in `build()`, or a condition over them. A `Text`, a
built-in widget's `String` property, and the `String` property of a custom widget your app
renders can join text and values:

```dart
final price = yearly ? widget.yearlyPrice : widget.monthlyPrice;
return Column(children: [
  Text('$price billed'),
  PlanBadge(label: 'Only $price a year'),
]);
```

Supported typed values and native `intl` formatting can also produce text inside
value objects, nested spans, and pure builder callbacks. See
[Dates and localized text](/authoring/host-data#dates-and-localized-text).

## Keep an interpolated string in one literal

Adjacent plain strings are joined as in Dart. A group of adjacent strings that mixes
plain and interpolated parts isn't supported, so keep the interpolation in one string:

```dart
// Instead of: Text('Hello, ' '$name')
Text('Hello, $name')
```

## Full width without double.infinity

A literal property in a surface can't carry `double.infinity` or another non-finite
number. Native builder constraints may be unbounded; guard them before using a finite
layout property. A literal `SizedBox(width: double.infinity)` stops the build with an
error. Use layout instead.

For one full-width child in a centered column, wrap it in a `Row` with `Expanded`:

```dart
Row(children: [Expanded(child: child)])
```

For a column that is full width throughout, stretch the cross axis:

```dart
Column(
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: [ /* ... */ ],
)
```

## Custom painting, gestures, and animation

Custom painting, such as a `CustomPainter`, goes in a custom widget that compiles into
your app. A surface sets it up through its constructor properties. You can often build
the same design from catalog widgets such as containers, gradients, and borders.
Native `ClipPath.shape` and direct `ShapeBorderClipper` construction accept supported
shape data; arbitrary `CustomClipper` methods stay in installed code. Recognized
native TextSpan recognizers use installed lifetime ownership; see
[Interactive surfaces](/authoring/interactive-surfaces#interactive-text-spans).
Lottie and Rive are outside the supported delivered authoring set.

These rules keep every surface something the app can render from data. When a surface
needs a component of your own, [custom widgets](/authoring/custom-widgets) are the way
to add it.
