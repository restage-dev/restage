---
title: Custom widgets
description: Name a widget from your own app, reuse it across surfaces and list it in the editor with one annotation, and generate RFW, A2UI, and Widgetbook output from the same class.
---

A custom widget is a widget from your own app, like a component from your design system. Surfaces can use it with no annotation. The build inlines it when it only composes other widgets, and renders it from your app when it can't.

Add `@RestageWidget()` to give it a name, reuse it across surfaces and list it in the editor's palette. From that one class, Restage generates:

- an entry in your RFW widget catalog, plus the code that builds the widget in your app
- optionally, an A2UI `CatalogItem` and its JSON Schema
- optionally, a Widgetbook v4 story

The unnamed public constructor defines the widget's inputs, and doc comments describe them. Add target annotations only for things Dart can't express.

## 1. Write plain Flutter first

Build the widget from normal Flutter widgets. Annotate the custom widget and the surface, and leave `Container`, `Text`, `Column` and everything else inside them as they are.

[Write a surface](/authoring/write-a-surface#plain-flutter-composition) has a compiled example.

## 2. Add the annotation

`@RestageWidget()` is usually all you need:

```dart
import 'package:flutter/material.dart';
import 'package:restage/restage.dart';

/// A card registered with only `@RestageWidget()`.
@RestageWidget()
class BareCatalogCard extends StatelessWidget {
  /// Creates the card.
  const BareCatalogCard({super.key, this.label = 'Bare catalog card'});

  /// Visible card label.
  final String label;

  @override
  Widget build(BuildContext context) => Card(child: Text(label));
}
```

That example has no `name`, `library`, `category`, property annotations or hand-written story. Restage fills them in:

- The class name becomes the catalog name.
- The unnamed constructor gives the order of the inputs, whether each is required or nullable, and its default.
- The doc comment on each field describes the property.
- With no category, Widgetbook lists the widget at the top level instead of guessing a group.
- The `@RestageLibrary` file that exports the widget says which library it belongs to.

Use `@RestageProperty` only for what Dart can't say: value constraints, a default taken from your theme, grouping in the editor, or a different description. A plain public constructor input needs no annotation.

## 3. Declare exact library ownership

A custom widget library is a Dart file that exports the widgets it owns, and only those:

```dart
import 'package:restage/restage.dart';

export 'widgets/bare_catalog_card.dart';
export 'widgets/status_panel.dart';
export 'widgets/feature_panel.dart';
export 'widgets/feature_row.dart';
export 'widgets/price_badge.dart';
export 'widgets/stat_tile.dart';

/// The custom widget library of the example package.
final class RestageWidgetbookLibrary extends WidgetLibrary {
  /// Creates the library.
  const RestageWidgetbookLibrary();

  @override
  final String namespace = 'restage_widgetbook_example.widgets';
}

/// The package's widget library.
const WidgetLibrary restageWidgetbookLibrary = RestageWidgetbookLibrary();

/// Declares the library's capability version for every generated target.
@RestageLibrary(library: restageWidgetbookLibrary, capabilityVersion: 4)
const restageWidgetbookCatalog = 0;
```

A widget belongs to the library whose file exports it. File names and class names don't matter. A widget with no library gets a warning, and designers can't place or edit it as a widget of its own. A widget exported from more than one library stops the build, and the error names the files involved. Raise `capabilityVersion` when a catalog change needs a newer version of your app.

Until you push a surface that uses the library, change it freely. There's no version to bump and nothing to reset. The first push that depends on a library version records it in `.restage/library-contracts/`. Commit that folder. From then on the build checks the library against the record. It stops with a message naming the widget or parameter when a change needs a new version or a declared break.

Adding a widget or a parameter is safe. Raise `capabilityVersion` and every version you published before keeps rendering.

Renaming, removing or retyping a widget or a parameter is a break. Declare it by raising `capabilityVersion` and setting `compatibleSince` to the same number. A new version is free to change again until a push depends on it. On the new build, published versions that need the older library use the mount's fallback, such as a bundled surface or your compiled widget. `restage surface check-libraries` lists those versions before you ship.

## 4. Add useful target-specific configuration

Target settings sit next to the field or class they affect. This example is compiled in the public example package. It adds a hint for the model, picks the value a callback writes back, and sets the Widgetbook preview states:

```dart
import 'package:flutter/material.dart';
import 'package:restage/a2ui.dart' as a2ui;
import 'package:restage/restage.dart';
import 'package:restage/widgetbook.dart' as wb;

/// The current state of a [CatalogShowcase].
enum CatalogShowcaseStatus {
  /// Ready for input.
  ready,

  /// Processing a change.
  processing,
}

/// Structured information displayed by a [CatalogShowcase].
class CatalogShowcaseData {
  /// Creates showcase information.
  const CatalogShowcaseData({required this.note, required this.count});

  /// Supporting text.
  final String note;

  /// The displayed count.
  final int count;
}

/// A catalog widget that feeds every enabled target from one source.
/// It combines ordinary state, an enum, a callback that writes a value back,
/// child widget inputs, and your own data class. The `hero`, `details`, and
/// `footer` inputs need no slot annotation.
///
/// This second paragraph also appears in the generated metadata, because
/// every paragraph of a doc comment is kept.
@a2ui.Config(
  usage:
      'Use to verify a custom-widget catalog across RFW, A2UI, and Widgetbook.',
)
@RestageWidget(category: WidgetCategory.input)
class CatalogShowcase extends StatelessWidget {
  /// Creates a catalog showcase.
  const CatalogShowcase({
    super.key,
    required this.title,
    this.enabled = true,
    required this.status,
    required this.onChanged,
    required this.hero,
    required this.details,
    this.footer,
    required this.data,
  });

  /// Visible title.
  final String title;

  /// Whether the control is enabled.
  @wb.Config.allValues()
  final bool enabled;

  /// Current state.
  @wb.Config.allValues()
  final CatalogShowcaseStatus status;

  /// Reports changes to [enabled].
  @a2ui.Config.writeBackValue('enabled')
  final ValueChanged<bool> onChanged;

  /// Custom widget shown before the detail list.
  final Widget hero;

  /// Detail widgets shown in source order.
  final List<Widget> details;

  /// Optional custom widget shown after the detail list.
  final Widget? footer;

  /// Structured information.
  final CatalogShowcaseData data;

  @override
  Widget build(BuildContext context) {
    return Column(
      mainAxisSize: MainAxisSize.min,
      crossAxisAlignment: CrossAxisAlignment.start,
      children: [
        hero,
        Text(title),
        Text('${status.name}: ${data.note} (${data.count})'),
        Switch(value: enabled, onChanged: onChanged),
        ...details,
        ?footer,
      ],
    );
  }
}
```

`a2ui.Config.usage` is a hint for the model that picks components. `a2ui.Config.writeBackValue('enabled')` says which value a callback writes back when more than one would fit. When only one fits, you can leave it out.

Any `Widget` or `List<Widget>` constructor input can take child widgets. `hero`, `details` and `footer` keep their names. A class can have as many of these as it needs, and none has to be called `child` or `children`.

Generated A2UI payloads all use the same layout. A2UI's own `id` and `component` keys stay at the top level, and each constructor input becomes a top-level property:

```json
{
  "id": "showcase",
  "component": "CatalogShowcase",
  "props_title": "Catalog proof",
  "props_enabled": true,
  "props_status": "ready",
  "props_hero": "hero_component_id",
  "props_details": [
    "detail_a_id",
    "detail_b_id"
  ],
  "props_footer": "footer_component_id",
  "props_data": {
    "note": "Generated once",
    "count": 2
  }
}
```

A property key is `props_<DartName>` when the name is a valid upstream UAX31 identifier that doesn't start with `encoded_`. Every other name, including `$value`, and every name starting with `encoded_`, uses `props_encoded_<hex>`. The hex is each UTF-16 code unit of the source name as exactly four lowercase digits. `$value` becomes `props_encoded_002400760061006c00750065`.

Reserving `encoded_` keeps a normal source name from colliding with an encoded one. Producers must use the property keys in the generated catalog schema and instructions. Dart constructor arguments and nested rich-data keys keep their original names.

`wb.Config.allValues()` makes Widgetbook generate a story for each other `bool` or enum value. Each field varies on its own by default. The class above gets the default story, one for `enabled: false` and one for `status: processing`. Use `wb.Config.values([...])` to pick specific values, or the class-level `wb.Config(expansion: ..., maxStories: ...)` for every combination.

RFW needs no callback settings. It reads callbacks from the constructor and uses the Dart property name as the event name. Its only setting, `rfw.Config`, turns RFW output on or off for one widget.

Each target checks its own inputs. A problem that only affects Widgetbook doesn't block A2UI, and a package that only uses Widgetbook doesn't need A2UI. If a target can't handle a required input, the build stops at its source line. An optional input is left out only when leaving it out gives the same result as its default.

## 5. Generate every enabled target once

For Widgetbook, add `widgetbook: 4.0.0-beta.14` to the source package's dependencies. It includes its generator. For A2UI, add the dependencies in the [A2UI guide](/tools/a2ui#add-the-dependencies). Keep `restage_codegen` and `build_runner` as dev dependencies. Then enable the outputs you want in `build.yaml`:

```yaml
targets:
  $default:
    builders:
      restage_codegen:user_a2ui_catalog:
        enabled: true
      restage_codegen:widgetbook_stories:
        enabled: true
```

These emitters don't need RFW bundling. Leave `bundled_runtime` at its default, `false`, and no generated surface assets get added to the app.

Run the build once. There's no separate step per target:

```sh
dart run build_runner build
```

The first build also creates `.restage/wire-ids.events.jsonl`, and your first push creates `.restage/library-contracts/`. Commit both. Together they keep widget IDs stable and record the library versions you've shipped.

For a reusable package, run this build and `restage library record` in the package before you publish it. Include those files, and expose them to consumer builds with `additional_public_assets: [.restage/**]` in its `build.yaml`. If you restrict a target's `sources`, include `.restage/**` there too. Every Dart workspace member must expose this state, including for `build_runner build --workspace`. [Design-system packages](/authoring/design-system-packages) has the full setup.

For custom widgets, the build writes:

- `lib/user_catalog.g.dart`, `lib/user_factories.g.dart`, and `.restage/build/widget_catalog/catalog.json` for the RFW catalog
- `lib/generated/restage_a2ui_catalog.g.dart` and `.restage/build/a2ui/restage_a2ui_catalog.a2ui.json` for A2UI
- `restage.generated/<class_name>.stories.dart` next to the source file, Widgetbook's matching `.stories.g.dart`, and `lib/components.g.dart` for Widgetbook v4

These are ordinary Widgetbook story files. Widgetbook's own generator still owns `Story`, controls, registration, the workbench app and deployment, and you don't write a story host or run another step.

## 6. Run the consumers

Generate first, then run the consumer. For A2UI, register `buildRestageCatalog()` with a `MessageProcessor`, feed it A2UI messages and mount an `A2uiSurface`. The [A2UI guide](/tools/a2ui#connect-a2ui-and-check-cached-bundles) shows the processor and its lifecycle.

For Widgetbook, put a workbench entry point under the source package's `lib/`:

```dart
import 'package:flutter/material.dart';
import 'package:widgetbook/widgetbook.dart' as widgetbook;

import 'components.g.dart';

void main() => widgetbook.runWidgetbook(
  widgetbook.Config(
    components: components,
    lightTheme: ThemeData.light(useMaterial3: true),
    darkTheme: ThemeData.dark(useMaterial3: true),
  ),
);
```

You can also use a separate workbench app that depends on the source package and Widgetbook and imports that package's `components.g.dart`. Generate the source package before you run the workbench. Neither consumer needs a Restage upload, a publish or `restage build push`.

These previews build your real Dart widgets. Test the delivered RFW and real host actions separately. Screen stories capture preview events, while custom-widget callback previews usually use no-op closures. Scalar and enum inputs have controls, but complex inputs and child slots don't always have visual editors.

## See them in the dashboard

Dashboard previews are a separate workflow. The dashboard needs a compiled build that contains your native widgets, and you push one when you add or change them:

```sh
restage build push                # your personal build, for your own preview
restage build push --env staging  # the build everyone in your organization sees
```

Without a build that includes your widgets, the dashboard can't show surfaces that use them. The same goes for the app-rendered widgets a surface gets from the build, because the render bundle compiles them like custom widgets. `restage surface push` tells you which command to run. A preview build doesn't install native code on users' devices or activate a surface. See [Push a build](/tools/cli#push-a-build) for environments and CI.

## Widgets with their own logic

A `@RestageWidget` whose `build()` can't be fully inlined is split instead of rendered whole. What the build can express is delivered as a shared component. One push restyles the widget everywhere it's used. The rest renders from your app, and the widget's state moves into its generated wrapper.

Take a plan card that only runs a press animation in code. Its layout, text and colors are delivered, and only the animation driver renders from your app.

The widget renders whole from your app when its library has no generated `part` line, or when a dependency's generated code is stale. The build prints a note, and delivered surfaces still set its arguments.

## Data classes, children, and callbacks

The build rebuilds your data classes from their public constructors. That covers nested values, supported lists, maps, records, enums and defaults. Every `Widget` and `List<Widget>` constructor input becomes a child property under its own name. Callbacks with no argument or one value argument keep their Dart names.

Taps on your widget's callbacks are measured, and so are taps inside the children you pass to its `Widget` and `List<Widget>` inputs. A wrapper such as a background or a card doesn't hide them. When the build can't measure a surface, it says why in a warning, and `restage surface push` repeats it.

The [target matrix](/authoring/custom-widget-target-matrix) lists what RFW, A2UI and Widgetbook each accept. A constructor input a target can't handle is a build error. What a widget's `build()` does never fails the build, because it's split or rendered from your app. The build doesn't drop data or ask you to write glue code to cover the gap.

## Screens use the same build

A `@Screen(surface: ...)` can also produce an A2UI component and a Widgetbook story next to its delivered surface. A2UI and Widgetbook work from the constructor, while RFW still compiles only the `build` tree, state and `SurfaceEvent`s. A `@Screen()` with no category can still be used inside a flow. See the complete [screen example](/authoring/write-a-surface#one-source-three-targets).

The build finds `@Screen` classes anywhere in the package. Folders don't set the category or the id, and the category comes from the annotation. Leave out the id to use the file name, or give one that stays the same if the file moves. The publication manifest records the category, id, contract and generated files.

This doesn't cover `@FlowGraph` or `@Paywall`. It also doesn't break a screen's widget tree into built-in A2UI components or copy Flutter, Material or Cupertino widgets into your catalog. Mount published screens, flows and paywalls with their generated `*Surface(...)` widgets. The [lower-level APIs](/authoring/write-a-surface#recommended-authoring-and-mounting-apis) are there when you need to supply the reference and fallback setup yourself.

## Watch mode

Under `build_runner watch`, editing an annotated widget or screen regenerates its story right away. Adding, removing or renaming an annotated class changes which files the build writes. Restart `dart run build_runner watch` after that. A full build rescans the package and removes story output it no longer needs.

Several `@RestageWidget` and `@Screen` classes can share a file. Invalid source stops the build before any output is written.

For gradient text and masks, see [Gradients and masks](/authoring/gradients-and-masks). Code that loads a fragment shader or decodes an image renders from your app automatically. Extract it into a custom widget when you want editor controls for it.
