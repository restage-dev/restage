---
title: Host data
description: Pass values your app already has into a surface, read them in the widget, and let the surface update only what changed.
---

A surface can show data your app already has: the user's name, a list of their habits, how many tasks are left. You pass those values as constructor arguments to the generated `<ClassName>Surface` widget. A design can also read values your app computes in `build()`, from a cubit's state, entitlements, products, clock dates, `defaultTargetPlatform` or design tokens. When a value changes, the surface rebuilds only the parts that read it. Host data stays on the device.

## Declare the data as constructor parameters

Write the screen like any widget that takes data. The constructor parameters of a `@Screen` or `@Paywall` class are its host data:

```dart
final class Habit {
  const Habit({required this.id, required this.name});
  final String id;
  final String name;
}

@Screen(id: 'habit_list', surface: Surface.general)
final class HabitList extends StatelessWidget {
  const HabitList({required this.habits, super.key});

  final List<Habit> habits;

  static const toggleDay = SurfaceEvent<Map<String, Object?>>('toggle_day');

  @override
  Widget build(BuildContext context) => Column(
        children: [
          for (final habit in habits)
            ListTile(
              title: Text(habit.name),
              onTap: surfaceEvent(toggleDay, {'id': habit.id}),
            ),
        ],
      );
}
```

A read of a parameter (`habits`, or `widget.habits` in a `State`) becomes a read of `data.context.habits` in the delivered surface. A `for` over a list parameter stays a loop. The device decides how many rows to show from the data, and `habit.name` inside the loop reads that row's field. String interpolation over a `String` parameter (`'Hi $name'`) works too. For localized dates, numbers and messages, use native `intl` expressions as shown below.

A collection `if` can filter the widgets inside that loop:

```dart
Column(
  children: [
    for (final habit in habits)
      if (habit.id == 'daily_walk') Text(habit.name),
  ],
)
```

The list contains only the matching children, in their original order. You can add `else`, nest conditions, or spread a list literal in a branch. Conditions accept booleans, equality against literals, and combinations with `!`, `&&` and `||`.

Filtered loops need an app built with a catalog that supports them (catalog capability 10). After upgrading, run `dart run build_runner build` and release the app before you publish filtered lists. That includes lists passed to custom widgets.

### What a parameter can be

A parameter can be any of these:

- a string, integer, finite double, boolean or `DateTime`
- a `List` or a `Map<String, …>` of those
- any of those made nullable
- a plain data class like `Habit` above, with public final fields of those types, an unnamed constructor and no behavior

The build uses the same field list to encode the value and to read fields like `habit.name`. The two always match.

### Types outside that list

Reading a parameter whose type is outside that list doesn't stop the build. When the result of the read is data, your app computes the value. Otherwise the widget that needs the object renders from your app. The class can also declare a parameter of another type, like an analytics tag or a callback for the app, and `build` can leave it alone.

Supported typed member and index expressions work in builder callbacks and value expressions. Arbitrary object getters and methods are computed in your app as values. The build report lists them as "App code computes".

## Dates and localized text

Pass a `DateTime` through a generated mount like any other typed constructor argument. Its microseconds since epoch and its UTC or local flag are kept, including inside lists and data classes. Write normal `intl` calls in the surface:

```dart
import 'package:intl/intl.dart';

Column(children: [
  Text('Starts ${DateFormat.yMMMd(locale).add_Hm().format(start)}'),
  Text(Intl.plural(count,
    one: 'One reminder',
    other: '$count reminders',
    locale: locale,
  )),
])
```

Supported `NumberFormat` constructors and configuration, `Intl.gender` and `Intl.select` use the same value mechanism, including nested strings and callback locals. Formatter calls keep Dart's argument evaluation order and native locale and error behavior.

Initialize date symbols for the locales your app uses, as you would with `intl`. If you omit the locale, `intl`'s normal default applies. Translated-message options such as `name` and `args` need an installed native binding. The build reports them when it can't prove that binding. `DateTime.now()` stays a computation in the installed app.

## Keyboard, accessibility and scaling

Read the keyboard inset and the text scaler from your `build` context, as you would in any Flutter widget:

```dart
final keyboard = MediaQuery.viewInsetsOf(context).bottom;
final scaler = MediaQuery.textScalerOf(context);
return Padding(
  padding: EdgeInsets.only(bottom: keyboard),
  child: Text('Add a reminder', textScaler: scaler),
);
```

All four `viewInsets` edges, `boldText`, `disableAnimations`, `accessibleNavigation` and `highContrast` update when their inherited values change. `Text` and `Text.rich` accept `TextScaler.noScaling`, `TextScaler.linear` and the exact scaler your app has at the generated mount's root context. A nonlinear scaler keeps its behavior at every font size. If you leave the scaler out, `Text` inherits one as usual. As in Flutter, you can't set a scaler and the deprecated `textScaleFactor` together.

Inside a builder callback, supported scalar reads come from the callback's own context. The build reports an opaque native value read from an unsupported descendant context. The root scaler can't stand in for that context's scaler, and a native binding that isn't available fails with an error. Native scaler bindings belong to the mounted subtree.

## Mount it with the generated widget

For every `@Screen(surface: ...)` the build generates a widget named `<ClassName>Surface` whose constructor matches yours. Pass the same arguments you'd pass to the widget itself:

```dart
HabitListSurface(
  habits: habits,
  onEvent: (event) {
    if (event is HabitListSurfaceToggleDayEvent) toggle(event.value['id']);
  },
)
```

The generated widget puts the host-data arguments into `context:` and shows the delivered surface. Your compiled `HabitList(habits: habits)` stays as the fallback. If delivery, rendering or an event fails, the user sees your widget with the same data.

To change the fallback, set an `unavailable` policy. See [Write a surface](/authoring/write-a-surface#typed-mounts).

A `@Paywall` class gets a generated widget too. [Write a surface](/authoring/write-a-surface#typed-mounts) lists the options it takes.

## Lower-level context maps

Direct runtime mounts take an optional `context:` map. Use it when you want to build the data map yourself instead of using a generated mount's typed inputs:

```dart
RestageScreen(
  screen: accountSummaryScreenRef,
  unavailable: const SurfaceScreenUnavailablePolicy.hide(),
  context: <String, Object?>{
    'profile': <String, Object?>{
      'displayName': profile.displayName,
      'tasksRemaining': remainingTasks.length,
    },
  },
)
```

`RestagePaywall`, `RestageFlowGraph`, `RestageFlowView` and `RestageScreenView` take the same parameter. The surface reads the values under `data.context.*`, the way the account summary screen above reads `profile.displayName`.

If your code manages a `DynamicContent` itself, `populateContextData(target, context)` writes the values into it. It always writes, without comparing against the previous values.

## How updates work

- **Values are checked and copied when you pass them.** Strings, integers, finite doubles, booleans, lists and maps with string keys are accepted. The limits are 32 levels of nesting below the root, 10,000 values in total including the root, and 100,000 map entries or list elements checked per update. Null map values are left out. Null list elements are removed and the list closes up.
- **Anything else is an error in a lower-level context map.** A raw `DateTime`, a closure, another object, a non-finite double or a cycle throws in debug. In release it's reported through `FlutterError` and left out, and the rest of the values still apply.
- **Equal values do nothing.** Passing a map with the same content doesn't update the surface. Passing `null` removes all the host data. Generated typed mounts encode `DateTime` arguments before this map boundary.
- **A single value change rebuilds what read it.** The widget that reads the value rebuilds, with its children. Widgets next to it that read other values don't.
- **A list change rebuilds the list and its rows, by position.** When a row is inserted or the list is reordered, state kept in a row stays at its position while your row ids move. Native `GridView` callbacks can keep keyed child state instead. See [Responsive layouts and grids](/authoring/widget-catalog#responsive-layouts-and-grids). Keep one number type per value. Values are compared with Dart `==`, and an `int` that later becomes a `double` at the same place can be missed.

## What host data is not

The SDK supplies device and theme values under `data.device` and `data.theme`. Your app supplies rendering inputs under `data.context`. There's no automatic `data.products` namespace. Pass product identifiers and localized prices through constructor parameters like other host data. See [Products and purchases](/paywalls/products-and-purchases) for store integrations.

Host data is input for rendering, and Restage keeps it on the device. Analytics removes `data.context.*` values from every event, and it isn't used for targeting. [Telemetry and data](/trust/telemetry) has the details. The server decides separately which version of a surface a user gets.

Host data can't add behavior either. It changes what a surface shows, while what a surface can do still comes from the widgets and actions compiled into your app. That includes the closures your own `build()` passes to widgets, as actions.
