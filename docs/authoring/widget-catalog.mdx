The catalog is the set of widgets a surface can use. Built-in widgets come from
three libraries; optional packages and your app can add more.

You don't need to look widgets up before you write a surface. You write the Flutter
widgets you already know, and the build finds them in the catalog. The catalog matters
when you want to know what's covered, or when you want to add a widget.

## The three libraries

| Library | Covers |
|---|---|
| [`restage_core`](https://pub.dev/packages/restage_core) | Layout, structure, and decoration: `Container`, `Column`, `Row`, `Stack`, `Text`, `Image`, `Directionality`, responsive builders, native grids, clipped shapes, and implicit animations. |
| [`restage_material`](https://pub.dev/packages/restage_material) | Material widgets: buttons, `Scaffold`, `AppBar`, `Card`, `ListTile`, chips, tabs, text fields, selection controls, and the interactive widgets below. |
| [`restage_cupertino`](https://pub.dev/packages/restage_cupertino) | iOS-style widgets: `CupertinoButton`, navigation bar and page scaffold, list sections, switches, sliders, pickers, and text fields. |

## You write ordinary Flutter

There are no separate widget classes to learn. You write `Container`, `Text`,
`Column`, `FilledButton`, and the rest with their normal Flutter APIs, and the build
maps each one to its catalog entry. A surface that uses `CupertinoButton` renders it
from the Cupertino library.

### Transforms

Use `Transform.translate` to move a child when painting while keeping its layout
space unchanged:

```dart
Transform.translate(
  offset: const Offset(12, -4),
  child: const Text('Moved'),
)
```

Offsets, `transformHitTests`, and `filterQuality` retain Flutter's behavior.

`Transform.scale` supports uniform scaling through `scale`, or independent axes
through `scaleX` and `scaleY`, including zero and negative factors:

```dart
Transform.scale(
  scaleX: -1,
  scaleY: 1.5,
  alignment: Alignment.center,
  child: const Text('Scaled'),
)
```

Origin, alignment, filtering, and hit testing follow Flutter. Omitting alignment
uses the native center default; passing `alignment: null` preserves null.

### Responsive layouts and grids

Use native builders for layout decisions that depend on the space their parent gives
this widget:

```dart
LayoutBuilder(builder: (context, constraints) {
  final width = constraints.hasBoundedWidth ? constraints.maxWidth / 2 : 80.0;
  return SizedBox(
    width: width,
    child: Text(width >= 200 ? 'Wide' : 'Compact'),
  );
})
```

`LayoutBuilder` reads local constraints. `OrientationBuilder` derives orientation
from its local space. Supported `Theme` and `MediaQuery` reads inside callbacks use
that callback's context. Pure callbacks can use immutable locals, conditions,
helper functions, typed captures, and finite child collections; see
[Builder callbacks](/authoring/constraints#builder-callbacks).

`GridView`, `.count`, `.extent`, `.builder`, and `.custom` use native standard grid
and child delegates. A builder requests items lazily and may return null, including
when `itemCount` is omitted. For a typed `habits` input:

```dart
GridView.builder(
  gridDelegate: const SliverGridDelegateWithFixedCrossAxisCount(
    crossAxisCount: 2,
  ),
  itemBuilder: (_, index) {
    if (index >= habits.length) return null;
    return Text(habits[index].name, key: ValueKey<String>(habits[index].id));
  },
  findChildIndexCallback: (key) {
    final id = (key as ValueKey<String>).value;
    final index = habits.indexWhere((habit) => habit.id == id);
    return index < 0 ? null : index;
  },
)
```

For reordered data, use stable scalar `ValueKey` values on returned roots and a
matching native key-to-index callback. Standard physics parent chains, native
cache values, and delegate flags retain their normal behavior. Explicit controller
objects and custom physics/delegates require installed application code.

### Direction and clipped shapes

Use `Directionality` and native `textDirection` arguments where Flutter exposes
them. `EdgeInsets.only(left: ...)` stays physical; `EdgeInsetsDirectional.only(start: ...)` follows direction. Directional alignment, corner radii, gradients, and
`DecorationImage` alignment resolve when Flutter renders them. A slot typed as
concrete `Alignment` or `EdgeInsets` still requires that concrete type.

```dart
Directionality(
  textDirection: TextDirection.rtl,
  child: ClipPath.shape(
    shape: const RoundedRectangleBorder(
      borderRadius: BorderRadiusDirectional.only(topStart: Radius.circular(16)),
    ),
    child: const Padding(
      padding: EdgeInsetsDirectional.only(start: 12),
      child: Text('Welcome'),
    ),
  ),
)
```

Plain `ClipPath` and direct `ShapeBorderClipper` construction also work. The static
`ClipPath.shape` method reads ambient direction; a direct `ShapeBorderClipper`
keeps its supplied nullable `textDirection`. Arbitrary `CustomClipper` methods
must live in installed application code. Directional radius recipes accept circular
corners; unsupported elliptical corners receive a diagnostic.

### Optional SVG

Add `restage_svg` and `flutter_svg` to your app's dependencies, then use the native
package APIs:

```dart
import 'package:flutter_svg/flutter_svg.dart';

SvgPicture.asset(
  'assets/illustration.svg',
  width: 160,
  semanticsLabel: 'Getting started',
)
```

`SvgPicture.network`, `.string`, `.memory`, and the unnamed constructor with a
supported `SvgAssetLoader`, `SvgNetworkLoader`, `SvgStringLoader`, or
`SvgBytesLoader` also work. Declare bundled assets in `pubspec.yaml` as usual. Package asset keys, network headers, byte data, `SvgTheme`, `ColorFilter`,
RTL mirroring, and declarative nullable `placeholderBuilder` callbacks retain
native behavior. Byte lists contain integers from 0 through 255 and are limited
to 1 MiB. Custom bundles, clients, color mappers, file loaders, arbitrary loader
subclasses, and unsupported error/image callbacks receive authoring diagnostics.
`SvgTheme.currentColor` and the color passed to `ColorFilter.mode` must be
non-null, proven base `Color` values. Subtypes such as `Colors.red`
(`MaterialColor`) are diagnosed, including through typed, dynamic, or imported
constant aliases. This applies both inside and outside callbacks. Ordinary
Flutter paint properties continue to accept their supported MaterialColor values.
Supported base Color constants retain their exact components and color space.
Placeholder callbacks read their native local context; a captured outer context
continues to refer to its original ancestor scope.

The SVG dependency is optional for apps that do not use this catalog.

### AppBar

`AppBar` supports its layout, text and icon styles, system-bar styles, opacity,
animation, and accessibility options. Use ordinary Flutter values such as
`TextStyle`, `IconThemeData`, and `SystemUiOverlayStyle`:

```dart
import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

AppBar(
  backgroundColor: Colors.transparent,
  systemOverlayStyle: SystemUiOverlayStyle.dark.copyWith(
    statusBarColor: Colors.transparent,
  ),
  iconTheme: const IconThemeData(size: 24, color: Colors.black),
  actionsIconTheme: const IconThemeData(color: Colors.blue),
  title: const Text('Welcome'),
)
```

Omitted styles, `centerTitle`, and `toolbarHeight` retain Flutter's theme and
platform defaults. The `bottom` slot accepts a `TabBar` or `PreferredSize`, and
`flexibleSpace` places content behind the toolbar.

`IconThemeData` supports its constructor, `IconThemeData.fallback()`,
`copyWith`, and `IconThemeData.lerp`. An `AppBar` used as another AppBar's
`bottom` may take a nullable `toolbarHeight`.

`notificationPredicate` accepts a depth check such as
`(notification) => notification.depth == 1`, where the depth is an `int`.
Omitting it keeps Flutter's default predicate.

### Tab pages

Combine `DefaultTabController`, `TabBar`, and `TabBarView` as you would in Flutter:

```dart
DefaultTabController(
  length: 2,
  child: Scaffold(
    appBar: AppBar(
      bottom: const TabBar(tabs: [Tab(text: 'One'), Tab(text: 'Two')]),
    ),
    body: const TabBarView(
      children: [Text('First page'), Text('Second page')],
    ),
  ),
)
```

`TabBarView` uses the nearest `DefaultTabController` and supports `clipBehavior`,
`dragStartBehavior`, and `viewportFraction`, including fractions greater than one.
Provide bounded space, such as the `Scaffold.body` above, and matching controller,
tab, and page counts. Explicit `controller` and `physics` expressions are not
currently compiled.

## Widgets with built-in gestures and animation

`restage_material` includes widgets whose gesture and animation code is compiled into
your app. A surface sets their properties and receives their events:

- `RestageModalSheet` and `RestageDraggableSheet` for bottom sheets you drag.
- `RestagePager` for pages you swipe.
- `RestageDropdown`, `RestageRadioGroup`, `RestageSegmentedButton`, and
  `RestageToggleButtons` for choosing an option.

`restage_core` adds motion widgets (`RestageMotion`, `RestageFadeIn`, `RestagePulse`,
`RestageStagger`) and number and price formatting (`RestagePrice`,
`RestageFormattedNumber`).

## Your own widgets

To use a widget from your design system in a surface, annotate it with
`@RestageWidget` and it joins the catalog. See [Custom widgets](/authoring/custom-widgets).

## One catalog for every surface

The same widgets build an onboarding flow, a message, a survey, a paywall, a single
card, or a whole screen. There is no separate catalog per surface type.
