You write a surface with the Flutter widgets you already know. The build looks each one up in the catalog and compiles it. A widget that isn't in the catalog renders from your app. Built-in widgets come from three libraries, and optional packages and your app can add more. You only need this page to see what's covered or to add a widget.

## The three libraries

| Library | Covers |
|---|---|
| [`restage_core`](https://pub.dev/packages/restage_core) | Layout, structure, and decoration: `Container`, `Column`, `Row`, `Stack`, `Text`, `Image`, `Directionality`, responsive builders, native grids, clipped shapes, and implicit animations. |
| [`restage_material`](https://pub.dev/packages/restage_material) | Material widgets: buttons, `Scaffold`, `AppBar`, `Card`, `ListTile`, chips, tabs, text fields, selection controls, and the interactive widgets below. |
| [`restage_cupertino`](https://pub.dev/packages/restage_cupertino) | iOS-style widgets: `CupertinoButton`, navigation bar and page scaffold, list sections, switches, sliders, pickers, and text fields. |

## You write ordinary Flutter

There are no separate widget classes to learn. You write `Container`, `Text`, `Column`, `FilledButton` and the rest with their normal Flutter APIs. A surface that uses `CupertinoButton` renders it from the Cupertino library.

### Transforms

`Transform.translate` moves a child when painting and leaves its layout space alone:

```dart
Transform.translate(
  offset: const Offset(12, -4),
  child: const Text('Moved'),
)
```

Offsets, `transformHitTests` and `filterQuality` behave as they do in Flutter.

`Transform.scale` takes a uniform `scale`, or `scaleX` and `scaleY` for each axis. Zero and negative factors work:

```dart
Transform.scale(
  scaleX: -1,
  scaleY: 1.5,
  alignment: Alignment.center,
  child: const Text('Scaled'),
)
```

Origin, alignment, filtering and hit testing follow Flutter. If you leave out `alignment` you get the native center default, and `alignment: null` stays null.

### Responsive layouts and grids

Use the native builders when a layout depends on the space the parent gives the widget:

```dart
LayoutBuilder(builder: (context, constraints) {
  final width = constraints.hasBoundedWidth ? constraints.maxWidth / 2 : 80.0;
  return SizedBox(
    width: width,
    child: Text(width >= 200 ? 'Wide' : 'Compact'),
  );
})
```

`LayoutBuilder` reads its local constraints, and `OrientationBuilder` works out orientation from its local space. `Theme` and `MediaQuery` reads inside a callback use that callback's context.

A callback can use immutable locals, conditions, helper functions, typed captures and finite child collections. See [Builder callbacks](/authoring/constraints#builder-callbacks).

`GridView`, `.count`, `.extent`, `.builder` and `.custom` use Flutter's standard grid and child delegates. A builder asks for items lazily and can return null, including when you leave out `itemCount`. Here `habits` is a typed input:

```dart
GridView.builder(
  gridDelegate: const SliverGridDelegateWithFixedCrossAxisCount(
    crossAxisCount: 2,
  ),
  itemBuilder: (_, index) {
    if (index >= habits.length) return null;
    return Text(habits[index].name, key: ValueKey<String>(habits[index].id));
  },
  findChildIndexCallback: (key) {
    final id = (key as ValueKey<String>).value;
    final index = habits.indexWhere((habit) => habit.id == id);
    return index < 0 ? null : index;
  },
)
```

If the data can be reordered, give the returned roots stable scalar `ValueKey` values and add a matching key-to-index callback.

Standard physics parent chains, cache values and delegate flags behave as they do in Flutter. Explicit controller objects and custom physics or delegates run in code installed in your app. The scrollable that holds one renders from your app automatically. A `ListView(controller: _scroll)` needs no change.

### Direction and clipped shapes

Use `Directionality` and the `textDirection` arguments where Flutter has them:

- `EdgeInsets.only(left: ...)` stays physical.
- `EdgeInsetsDirectional.only(start: ...)` follows the direction.
- Directional alignment, corner radii, gradients and `DecorationImage` alignment resolve when Flutter renders them.
- A slot typed as concrete `Alignment` or `EdgeInsets` still needs that concrete type.

```dart
Directionality(
  textDirection: TextDirection.rtl,
  child: ClipPath.shape(
    shape: const RoundedRectangleBorder(
      borderRadius: BorderRadiusDirectional.only(topStart: Radius.circular(16)),
    ),
    child: const Padding(
      padding: EdgeInsetsDirectional.only(start: 12),
      child: Text('Welcome'),
    ),
  ),
)
```

Plain `ClipPath` and direct `ShapeBorderClipper` construction work too. The static `ClipPath.shape` method reads the ambient direction, while a direct `ShapeBorderClipper` keeps the nullable `textDirection` you give it.

Directional radius recipes take circular corners. Elliptical corners render from your app, and so does a `CustomClipper` with its own methods.

### Optional SVG

Add `restage_svg` and `flutter_svg` to your app's dependencies. Then use the `flutter_svg` API as usual:

```dart
import 'package:flutter_svg/flutter_svg.dart';

SvgPicture.asset(
  'assets/illustration.svg',
  width: 160,
  semanticsLabel: 'Getting started',
)
```

`SvgPicture.network`, `.string` and `.memory` work too, and so does the unnamed constructor with an `SvgAssetLoader`, `SvgNetworkLoader`, `SvgStringLoader` or `SvgBytesLoader`. Declare bundled assets in `pubspec.yaml` as you normally would.

These behave as they do in `flutter_svg`:

- Package asset keys and network headers.
- Byte data. A byte list holds integers from 0 through 255 and is limited to 1 MiB.
- `SvgTheme`, `ColorFilter` and RTL mirroring.
- Nullable `placeholderBuilder` callbacks. A placeholder callback reads its own local context, while a captured outer context still points at its original ancestor scope.

Custom bundles, HTTP clients, color mappers, files, loaders and typed error and image callbacks work when your app passes them in from outside `build()`, like `bundle: bundle` from a field. Written inline in `build()`, like `bundle: rootBundle`, an inline `ColorMapper`, your own `BytesLoader` subclass or an inline `errorBuilder` closure, they make the `SvgPicture` render from your app.

`SvgTheme.currentColor` and the color you pass to `ColorFilter.mode` can be any `Color`, including a `MaterialColor` such as `Colors.red`, directly or through a dynamic or imported constant, and the swatch is kept. Base `Color` constants keep their exact components and color space. A null color makes the `SvgPicture` render from your app.

If your app doesn't use SVG, you don't need the dependency.

### AppBar

`AppBar` supports its layout, text and icon styles, system-bar styles, opacity, animation and accessibility options. Pass ordinary Flutter values such as `TextStyle`, `IconThemeData` and `SystemUiOverlayStyle`:

```dart
import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

AppBar(
  backgroundColor: Colors.transparent,
  systemOverlayStyle: SystemUiOverlayStyle.dark.copyWith(
    statusBarColor: Colors.transparent,
  ),
  iconTheme: const IconThemeData(size: 24, color: Colors.black),
  actionsIconTheme: const IconThemeData(color: Colors.blue),
  title: const Text('Welcome'),
)
```

If you leave out the styles, `centerTitle` or `toolbarHeight`, Flutter's theme and platform defaults apply. The `bottom` slot takes a `TabBar` or `PreferredSize`, and `flexibleSpace` puts content behind the toolbar.

`IconThemeData` supports its constructor, `IconThemeData.fallback()`, `copyWith` and `IconThemeData.lerp`. An `AppBar` used as another `AppBar`'s `bottom` can take a nullable `toolbarHeight`.

`notificationPredicate` takes a depth check such as `(notification) => notification.depth == 1`, where the depth is an `int`. If you leave it out, Flutter's default predicate applies.

### Tab pages

Combine `DefaultTabController`, `TabBar` and `TabBarView` the way you would in Flutter:

```dart
DefaultTabController(
  length: 2,
  child: Scaffold(
    appBar: AppBar(
      bottom: const TabBar(tabs: [Tab(text: 'One'), Tab(text: 'Two')]),
    ),
    body: const TabBarView(
      children: [Text('First page'), Text('Second page')],
    ),
  ),
)
```

`TabBarView` uses the nearest `DefaultTabController`. It supports `clipBehavior`, `dragStartBehavior` and `viewportFraction`, including fractions above one.

Give it bounded space, as `Scaffold.body` does above. The controller, tab and page counts have to match. A `TabBarView` with an explicit `controller` or `physics` isn't delivered and renders from your app instead.

## Widgets with built-in gestures and animation

`restage_material` includes widgets whose gesture and animation code is compiled into your app. A surface sets their properties and receives their events:

- `RestageModalSheet` and `RestageDraggableSheet` for bottom sheets you drag.
- `RestagePager` for pages you swipe.
- `RestageDropdown`, `RestageRadioGroup`, `RestageSegmentedButton` and `RestageToggleButtons` for choosing an option.

`restage_core` adds motion widgets (`RestageMotion`, `RestageFadeIn`, `RestagePulse`, `RestageStagger`) and number and price formatting (`RestagePrice`, `RestageFormattedNumber`).

## Your own widgets

A surface can use a widget from your design system with no annotation. Annotate it with `@RestageWidget` to add it to the catalog and the editor's palette. See [Custom widgets](/authoring/custom-widgets).

## One catalog for every surface

Onboarding flows, messages, surveys, paywalls, single cards and whole screens all use the same widgets. There's no separate catalog per surface type.
