---
title: Write a surface
description: Turn a Flutter widget you already wrote into a surface with one annotation, and optionally generate A2UI and Widgetbook output from the same class.
---

Restage lets you change a screen in your Flutter app after you've shipped it. You add `@Screen` to a widget you already have, run `build_runner`, and publish. The app shows what you published. Until then, it shows your widget as written.

## Start with a widget you have

Pick one small piece of your UI and leave its layout, theme, helper widgets and local state where they are. Your router, state management and services stay in your app. If the widget already compiles, you don't need to split it up.

Say `WelcomeBanner` lives in `lib/welcome_banner.dart`. Add an import, a `part` line and the annotation:

```diff
 import 'package:flutter/material.dart';
+import 'package:restage/restage.dart';
+
+part 'restage.generated/welcome_banner.restage.g.dart';

+@Screen(id: 'welcome_banner', surface: Surface.message)
 final class WelcomeBanner extends StatelessWidget {
```

Leave the constructor and `build()` alone. Then run the build:

```sh
dart run build_runner build
```

Swap the widget in your app for the one the build generated:

```diff
-WelcomeBanner(name: user.name)
+WelcomeBannerSurface(name: user.name)
```

`WelcomeBannerSurface` takes the same arguments as `WelcomeBanner`. It sends the ones that are [host data](/authoring/host-data), like `name`, to the published screen. It also runs a copy of your `build()` and records every other value the screen reads, such as ones your state or providers compute.

If delivery isn't set up or something fails, users see your compiled `WelcomeBanner`. Leave `bundled_runtime` off. The fallback needs no surface assets and no published version. Parts that render from your app keep their `State` when the screen switches between the published version and your widget. A widget value your build places in several spots keeps a separate `State` at each one, as it does in Flutter.

### Leave the rest to the build

Annotate the widget as it is and run the build. Code the build can't deliver doesn't fail it. That part keeps rendering from your app's compiled code, and the rest of the screen is still delivered. Run the report to see the split:

```sh
restage build report
```

[What renders from your app](/authoring/islands) explains the report. After that:

- Leave the parts that render from your app alone unless you want them changeable over the air.
- Treat warnings as real work. Each one tells you a value or widget will be dropped, or that only an app release can change it.
- Don't write a second copy of the screen.
- Fix the few things that still stop the build before you mount the surface. The fallback won't cover for code the build rejects.

Keep the rest of your app code where it is:

- Leave app logic in the class that owns it. Connect it with surface events, or with a normal callback that calls it.
- Keep [local state](/authoring/interactive-surfaces) in the widget. On a paywall or a `@Screen(surface: ...)`, its `State` fields and lifecycle methods keep running in your app. A flow step's `State` has to become delivered state, and it runs as written only when the step falls back to your compiled widget.
- Leave controllers and platform views where they are. The widget that holds one renders from your app.
- Test the compiled widget and the published screen with the same inputs and taps.

## Plain Flutter composition

Write the screen with ordinary Flutter widgets, your theme and your own components. Don't wrap built-in widgets or annotate them. This `build` method comes from the public example package, where it's compiled and tested:

```dart
@override
Widget build(BuildContext context) {
  return Center(
    child: ElevatedButton(
      key: const ValueKey('get-started-action'),
      onPressed: surfaceEvent(continueEvent, 'preview'),
      child: const Text('Get started'),
    ),
  );
}
```

The build delivers the `build()` tree it can express. What it can't express renders from your app as values, actions and islands, and the root listeners and providers stay in your app for every design. A few cases have their own pages:

- Responsive builders, lazy grids, directional geometry and clipped shapes use plain Flutter syntax. See the [Widget catalog](/authoring/widget-catalog).
- For exact text scaling, keyboard and accessibility reads, dates and localized text, see [Host data](/authoring/host-data).
- Tappable text uses [native TextSpan recognizers](/authoring/interactive-surfaces#interactive-text-spans).
- SVG works through the optional `restage_svg` package.

If the build hits code it can't express, it doesn't stop. That part renders from your app and the rest stays delivered. The build report says what share of the widgets a design can change.

The app needs generated code for everything in that list. It also needs it for any new app-rendered widget, any new computed value and any new action. When you start using one of them, run the build and release that app version first. Publish content that uses it once users have that version:

```sh
dart run build_runner build
```

## Pick the annotation

`@Screen` is for one screen, or one part of a screen, that you publish by itself. The `surface:` value is its category:

```dart
@Screen(id: 'message_notice', surface: Surface.message)
final class MessageNotice extends StatelessWidget {
```

A step inside a flow takes `@Screen()` with no category. The flow handles navigation for it:

```dart
@Screen()
class StarterStatsScreen extends StatelessWidget {
```

Use `@FlowGraph` when you want Restage to run the whole journey: the order of screens and how they connect. You write it in Dart, usually as a `FlowDefinition`:

```dart
@FlowGraph(id: 'message_offer', surface: Surface.message)
const messageOffer = FlowDefinition(
  start: MessageNotice, // The first screen.
  transitions: [
    // An event on a screen, and the screen it leads to.
    Transition(MessageNotice.openOffer, to: UpgradeOffer),
    // Ends the flow here.
    Transition.complete(UpgradeOffer.continueFlow),
  ],
);
```

The start screen, the transitions and the events are all Dart types and constants, with no string names to get wrong. If your graph won't fit in a const object, use the class form, `RestageFlow`. See [Flows overview](/flows/overview).

Use `@Paywall()` for an offer that needs the paywall lifecycle and purchase events:

```dart
@Paywall()
class ProUpgradePaywall extends StatelessWidget {
```

Use `@RestageWidget()` to name a component of your own, reuse it across surfaces or give it properties in the editor. Surfaces can already use your app's widgets without it. To show it in the editor's palette it needs a [library export](/authoring/custom-widgets):

```dart
@RestageWidget()
class BareCatalogCard extends StatelessWidget {
```

A screen's category is one of `onboarding`, `message`, `survey`, `paywall` or `general`:

- Pick `general` when nothing else fits.
- A screen with a category only works in a flow of the same category.
- A `@Paywall()` works as a step in any flow.
- `Surface` is just the enum. There's no `@Surface` annotation.

On flows and paywalls:

- You don't have to use a flow. Your existing routes can keep showing individual surfaces.
- Before you rewrite navigation between existing paywalls, check the [automatic Navigator conversion](/paywalls/overview#multi-screen-paywalls).
- `@Paywall()` gives you the paywall lifecycle and the events purchase adapters listen for. The purchase itself still runs in your app.
- A plain `@Screen(surface: Surface.paywall)` fires ordinary screen events instead.

The build finds annotations anywhere in your package:

- Folders don't set a category or an id.
- With no id, the build uses the file name. Set one yourself if the file might move.
- Keep the `part 'restage.generated/<file>.restage.g.dart';` line. That's where the build writes the generated code.
- One file gets one generated part, whether it holds a screen, a flow or both.
- Generated files go in a `restage.generated/` folder next to your file.

## One source, three targets

Here's a complete screen from the [Widgetbook example source](https://github.com/restage-dev/restage/blob/main/packages/restage_widgetbook_example/lib/onboarding/screens/welcome_screen.dart). A test checks this snippet against the compiled source:

```dart
import 'package:flutter/material.dart';
import 'package:restage/a2ui.dart' as a2ui;
import 'package:restage/restage.dart';
import 'package:restage/widgetbook.dart' as wb;

part 'restage.generated/welcome_screen.restage.g.dart';

/// An onboarding screen with a Continue action.
@a2ui.Config.usage('Use for the first screen of a native onboarding flow.')
@Screen(id: 'welcome_screen', surface: Surface.onboarding)
final class WelcomeScreen extends StatelessWidget {
  /// Creates the screen.
  const WelcomeScreen({
    super.key,
    required this.title,
    this.tone = WelcomeScreenTone.calm,
  });

  /// Event fired by the Continue action.
  static const continueEvent = SurfaceEvent<String>('continue');

  /// The screen title.
  final String title;

  /// The screen's tone. Widgetbook previews each value.
  @wb.Config.allValues()
  final WelcomeScreenTone tone;

  @override
  Widget build(BuildContext context) {
    return Center(
      child: ElevatedButton(
        onPressed: surfaceEvent(continueEvent, 'welcome'),
        child: Text(title),
      ),
    );
  }
}

/// The tone of a [WelcomeScreen].
enum WelcomeScreenTone { calm, urgent }
```

One class feeds two views of the screen:

- RFW is the format Restage delivers. It carries the delivered part of the `build()` tree, its events and the values the screen reads. If the tree never reads a constructor field, that field isn't in the published screen. If the tree reads a field whose type can't cross as data, your app computes the value, or the widget that needs the object renders from your app.
- A2UI and Widgetbook use the unnamed constructor. They build the real `WelcomeScreen` with `title`, `tone` and any other properties, and never look inside the widget tree.

Your property names stay as you wrote them. A field named `data`, `context` or `itemContext` won't clash with generated code. A property named `description` or `usage` won't be replaced by Widgetbook's own settings.

`a2ui.Config.usage` is a hint for the model that builds A2UI output. `wb.Config.values([false])` and `wb.Config.allValues()` on a field pick which states Widgetbook previews.

RFW needs no annotations. Events come from your `SurfaceEvent` declarations, and a custom widget's callbacks come from its constructor.

## Generate A2UI and Widgetbook output

RFW output is always on. To get A2UI and Widgetbook output too, enable them in your package's `build.yaml`:

```yaml
targets:
  $default:
    builders:
      restage_codegen:user_a2ui_catalog:
        enabled: true
      restage_codegen:widgetbook_stories:
        enabled: true
```

These two options don't need RFW bundling. Leave `bundled_runtime` at its default, `false`, and don't add any generated surface assets to your app.

Then run the build again. One run generates every target you enabled:

```sh
dart run build_runner build
```

Connect the output to [A2UI](/tools/a2ui#connect-a2ui-and-check-cached-bundles) or your [Widgetbook workbench](/authoring/custom-widgets#6-run-the-consumers).

## What the build writes

For `lib/onboarding/screens/welcome_screen.dart`, one run writes:

- `WelcomeScreenSurface` and the screen's reference, in `lib/onboarding/screens/restage.generated/welcome_screen.restage.g.dart`.
- The compiled screen (RFW text, RFW binary and the capability manifest), in one `welcome_screen.rsbundle` file under `.restage/build/bundles/lib/onboarding/screens/`. If you [bundle surfaces with the app](/delivery/bundled-assets), it goes under `assets/restage/bundles/` in your Flutter assets instead.
- `.restage/build/metadata/restage.publication.json`, the publication manifest. `restage surface push` reads it.
- With A2UI on: the screen's entry in `lib/generated/restage_a2ui_catalog.g.dart` and `.restage/build/a2ui/restage_a2ui_catalog.a2ui.json`.
- With Widgetbook on: `lib/onboarding/screens/restage.generated/welcome_screen.stories.dart`, Widgetbook's matching `.stories.g.dart`, and the screen's entry in `lib/components.g.dart`.

`welcomeScreenRef` is the generated reference to the screen, holding its category, id, contract version, capabilities and typed events. The build makes one for every annotated screen or flow class.

In A2UI, the screen becomes one component named after its id. In Widgetbook, the real class shows up under `Screens`, and the generated story setup handles its events. You don't write a Widgetbook host.

## Typed mounts

Every `@Screen(surface: ...)` also gets a widget called `<ClassName>Surface`, in the same generated file. A `@Screen()` with no category is a flow step and doesn't get one.

```dart
WelcomeScreenSurface(
  // Same constructor as WelcomeScreen. No string id.
  title: 'Welcome',
  onEvent: (event) {
    // The event class is the screen class, then `Surface`, then the event field.
    if (event is WelcomeScreenSurfaceContinueEventEvent) next(event.value);
  },
)
```

The event field here is `continueEvent`. Its class is `WelcomeScreenSurfaceContinueEventEvent`.

`WelcomeScreenSurface` is app code. It does these things:

- It sends the constructor arguments that are [host data](/authoring/host-data) to the screen, in `context:`.
- It runs a copy of your `build()` and records the values, conditions, loop items and app-rendered widgets the screen reads, where your build produces them.
- It holds your actions and owns your `State`. Root listeners and providers stay around every design.
- It registers the widgets that render from your app. You don't call anything at startup.
- It shows the published screen through `RestageScreen<E>`.
- It builds your own widget with the same arguments and keeps it as the fallback. If delivery, rendering or an event fails, users see that compiled widget.

Besides your own parameters, it takes `onEvent`, `resolver`, `onUnavailable` (called when the screen is unavailable), `loadingBuilder` and an optional `unavailable` policy. Leave `unavailable` out and users see the compiled widget. To hide an unavailable card or banner instead:

```dart
WelcomeScreenSurface(
  title: 'Welcome',
  // Show nothing when the screen is unavailable.
  unavailable: const SurfaceScreenUnavailablePolicy.hide(),
)
```

To show something else, pass your own fallback. The generated host data still applies:

```dart
WelcomeScreenSurface(
  title: 'Welcome',
  unavailable: SurfaceScreenUnavailablePolicy.fallback(
    builder: (_, error) => Text('Screen unavailable: ${error.reason.name}'),
  ),
)
```

Flows get a generated `<FlowName>Surface` too. See [Mount the flow](/flows/overview#mount-the-flow).

`RestageScreen` and `RestageFlowGraph<R>` still work when you want to pass references and fallback policies yourself. See [API choices](#recommended-authoring-and-mounting-apis).

A `@Paywall()` class gets its own `<ClassName>Surface`. It shows the paywall through `RestagePaywall` and keeps your widget as the fallback. It takes `onEvent`, `resolver`, `errorBuilder` and `loadingBuilder`.

The build skips generating the widget, and tells you why, in two cases. One is when its name would clash with one of your own declarations. The other is when it can't tell where a constructor argument comes from. If the screen needs values, app-rendered widgets, kept wrappers or `State` from that widget, the build reports an error for each instead, and names it.

The RFW files are data the SDK renders, while the generated A2UI and Widgetbook files are Dart code in your app and your workbench. Treat them like any other generated source.

## Test a mounted surface

A generated mount loads its content asynchronously. The first frame is empty.

```dart
testWidgets('shows the upgrade paywall', (tester) async {
  await tester.pumpWidget(
    const MaterialApp(home: ProUpgradePaywallSurface()),
  );
  // Pump once more after pumpWidget, or call pumpAndSettle.
  await tester.pump();

  expect(find.text('Go Pro'), findsOneWidget);
});
```

Without hosted delivery set up, the mount shows your compiled widget. Your test doesn't need a server.

## What A2UI and Widgetbook leave out

They only cover your own screens and widgets. They don't:

- add Flutter, Material, Cupertino or Restage built-in widgets to the A2UI catalog;
- split a screen's widget tree into separate A2UI components;
- cover `@FlowGraph` or `@Paywall`; or
- check that targets you deploy separately came from the same build.

If a target can't handle something, it tells you at the source line. No target drops an event or a field to let another target pass.

## Watch mode

While `build_runner watch` runs, edits inside an annotated class regenerate the A2UI and Widgetbook output right away. That includes constructor defaults, doc comments and Widgetbook values.

```sh
dart run build_runner watch
```

If you add, remove or rename an annotated class, restart the watcher, because that changes which files the build writes. A full build rescans the package and removes output it no longer needs.

## Build errors

The build delivers a broad part of Flutter and renders the rest from your app. A short list of things still stops it with an error at the source line:

```sh
dart run build_runner build
```

[What renders from your app](/authoring/islands#what-still-stops-the-build) lists them. [Authoring constraints](/authoring/constraints) has the rules for what a design can change. [Custom widgets](/authoring/custom-widgets) and the [target matrix](/authoring/custom-widget-target-matrix) show what each target accepts from a constructor.

## Recommended authoring and mounting APIs

In new code, use `@Screen`, `@Paywall` and `@FlowGraph`. For a flow, start with a `FlowDefinition`, and use the `RestageFlow` class form if you need its graph builder.

Mount with the generated `<ClassName>Surface`. It fills in the typed inputs, the widget registration, the placement name and the fallback to your compiled widget.

Every generated mount gets a placement automatically, without you naming one or calling a special constructor. To open the mount as a route, use `Restage.presentPlacement`:

```dart
Restage.presentPlacement(
  context,
  builder: (_, presentation) => WelcomeScreenSurface(title: 'Welcome'),
);
```

[Placements](/delivery/placements) also covers explicit placement APIs, for integrations that need them.

You can also mount `RestageScreen`, `RestagePaywall` and `RestageFlowGraph` directly. You pass the references or ids and set up the fallback yourself. These APIs still work and aren't going away.

[Hosted delivery](/delivery/hosted-delivery#fallbacks-by-mount-api) lists what each one needs. The deprecated aliases are under [Older names](#older-names).

## Older names

These older names still work. In new code, use the ones after the `+`:

```diff
-@ScreenSource
-@PaywallSource
-@FlowSource
+@Screen
+@Paywall
+@FlowGraph(surface: ...)
-RestageOnboarding
+<FlowName>Surface
```

`RestageOnboarding` still hosts onboarding flows. `RestageFlowGraph<R>` is the lower-level flow host, and it isn't deprecated.

Restage 2.0 renamed the host widgets to match the annotations. The old names still work as deprecated aliases in the current source:

```diff
-RestageSurfaceScreen<E>
+RestageScreen<E>
-RestageSurfaceFlow<R>
+RestageFlowGraph<R>
-RestageSurfaceScreenResolver
+RestageScreenResolver
```
