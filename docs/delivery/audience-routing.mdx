title: Audience routing
description: Target audiences, roll out versions and schedule delivery changes.
---

Routing decides which published content each audience gets in an environment. A
[placement](/delivery/placements) uses a delivery plan to pick content that fits a mount
in your app. Generated `*Surface(...)` widgets declare their placements for you. They
need no special constructor for routing.

## Choose the rule

A placement rule picks a live surface, and that surface's rules then pick an exact published version. Use a percentage rollout to deliver a version gradually, or an [experiment](/delivery/experiments) to compare outcomes under a statistical design. A
rollout alone doesn't produce a statistical winner.

An activated placement experiment beats placement rules. An activated surface experiment
beats that surface's version rules. If an experiment must enroll a user, an ordinary rule
never routes that user elsewhere.

Rules run in order:

- Disabled rules, closed time windows and nonmatching audiences are skipped.
- The first matching rule whose destination fits the app wins.
- If that destination doesn't fit, evaluation continues to the next rule.
- After the last rule, the default is checked too. If the default doesn't fit, the
  mount uses its fallback.

In the dashboard, pick a saved audience revision, or combine conditions over platform,
OS, app build, country, language, device and custom attributes. The inline editor
combines conditions with AND. A missing observed attribute normally doesn't match, but a missing audience definition is an error.

New rules start at the lowest priority. Before you reorder, check for rules that overlap
or hide later rules.

## Roll out or schedule a change

To roll a version out gradually, upload the candidate while the current default keeps
serving. Add a surface rule with the audience you want, a small primary share and the
current default as its remainder. Check fit, then review and publish the plan. Check
real renders and data coverage before you raise the share.

An installation stays in the same share while the rule, its allocation id and its scope
stay the same. Raising only the percentage keeps existing installations where they are.
For a share between 0% and 100%, an installation with no install id gets the remainder.
If the chosen branch doesn't fit, evaluation moves on to the next rule. It never switches
to the other branch.

The placement editor currently creates single-surface rules and keeps existing percentage rules.

A rule's time window includes its start and excludes its end. A scheduled plan replaces
the whole policy before it. Both use each device's local time, worked out from server
time and the offset the device reports. Your own time zone plays no part. When a device's
local time can't be worked out, the mount falls back with `localClockUnavailable`.

Before you change scheduled work, look at the complete timeline. Test matching and
nonmatching audiences, missing attributes, both rollout branches, older builds and window
boundaries.

Fit checks use the build requirements Restage has observed. A build with no observations
isn't proven compatible. After you publish, verify [delivery](/delivery/hosted-delivery)
on a device.

## Inspect the target

[Sign in and select your project, app and environment](/tools/cli#sign-in). The examples
use an onboarding flow with the id `welcome_flow`. Replace it with your surface id and
category. If an environment exists on both planes, pass `--plane sandbox` or
`--plane live`.

```sh
restage surface routing list-audiences --json
restage surface routing read welcome_flow --type onboarding --json
restage delivery placements list --json
```

An audience reference points to one fixed revision of that audience. A policy keeps the
revision it was reviewed against. Before you replace one, check where it's used:

```sh
restage surface routing audience-usage --audience-revision-id <id>
```

The CLI lists audiences and shows their usage. It can't create or edit them.

## Simulate and review a policy

For placement policies, use the placement
[delivery plan workflow](/delivery/placements#inspect-and-change-delivery). The surface
routing API takes complete typed policy requests:

- `preview --document` takes a `DeliveryPolicySimulationRequestV1`.
- `review --request` takes a `DeliveryPolicyReviewRequestV1`.
- `publish --review` takes the complete original `DeliveryPolicyReviewV1` the server
  returned.

`restage_measurement_schema` exports these types. Build them for the selected target and
serialize them exactly as the schema encodes them. Output from `routing read --out` is a policy document that you can't use as a review request.

Write new rules in the dashboard. The public schema can build whole plans and schedules, but it has no constructors for the rules inside them.

With valid simulation and review-request files for the same target:

```sh
restage surface routing preview welcome_flow --type onboarding \
  --document simulation.json --json
restage surface routing review welcome_flow --type onboarding \
  --request review-request.json --out routing-review.json
restage surface routing publish welcome_flow --type onboarding \
  --review routing-review.json
```

`preview` simulates the current saved policy without enrolling users, and its request has no candidate-plan field. The separate review evaluates the complete plan you propose.

Read the impact and warnings in the review before you publish. An agent must explain new
experiment impact and stop unless you've authorized it. Don't edit the review file. To
accept measurement warnings you've approved, add `--reviewed-digest` with the exact digest
of that review. The interactive CLI can ask for this acknowledgment separately. `--yes`
only confirms the live change.

A refusal blocks publication. If the policy or its impact changes, or the review is out
of date, get a new review. Pass a lowercase UUIDv4 as `--operation-id`. If you retry,
reuse it with the same review and acknowledgment.

Placement delivery plans work differently. `delivery plan publish --acknowledgement` takes
a `DeliveryMeasurementImpactAcknowledgementV1` JSON file instead of the digest flag. See
[Placements](/delivery/placements#inspect-and-change-delivery).

## Restore one route

`review-rollback` reviews a single route from an earlier revision and leaves the other
routes alone. Give it the route id, the prior revision ordinal and the expected
current policy ordinal:

```sh
restage surface routing review-rollback welcome_flow --type onboarding \
  --route-id ROUTE_ID --prior-revision-ordinal 2 \
  --expected-revision-ordinal 3 --out rollback-review.json
restage surface routing publish welcome_flow --type onboarding \
  --review rollback-review.json
```

Replace the example ordinals and route id with values from your policy history.
Policies with structured schedules need a whole-policy review instead.

## Use an agent or the TUI

The [MCP tools](/tools/mcp-server) do the same reads, previews, reviews, publishes and
route rollbacks. Call `restage_review_routing` before `restage_publish_routing`, and pass the publish tool the original review bytes.

- Pass `reviewedDigest` only for measurement warnings you've approved.
- If you retry, reuse the same `operationId`.
- `confirmLive` confirms a live change separately.
- Placement plan tools take `requestJson` with the publish request's review reference
  and acknowledgment.

The tool schemas list the required fields.

In `restage console`, press `/` and run the same commands, including the `restage`
prefix. The selected target supplies defaults, and revision checks and live-write confirmation still apply. The TUI doesn't acknowledge measurement warnings for you. Supply the approved digest, or use a terminal for interactive approval.
