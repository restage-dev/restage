A paywall is a Flutter widget with `@Paywall()` on it. You mount its generated widget in your app. Paywalls use the same widget catalog, compiler and delivery as onboarding flows, messages and surveys. See [How it works](/concepts/how-it-works).

A paywall never starts a purchase itself. Its buttons send events, and your app runs the purchase with the store library it already uses. A purchase closure written inline in the paywall, like `onPressed: () => cubit.purchase(plan)`, becomes an action that your app runs. The published paywall still never purchases. The store library can be the [RevenueCat adapter](/paywalls/revenuecat), the [native store bridge](/paywalls/native-stores) or your own purchase service.

## Write a paywall

Save this as `lib/paywalls/pro_upgrade.dart`. With no id, the paywall's id comes from the file name. Pass an explicit id if you want a different one, or one that survives moving the file.

```dart
import 'package:flutter/material.dart';
import 'package:restage/restage.dart';

part 'restage.generated/pro_upgrade.restage.g.dart';

@Paywall()
class ProUpgradePaywall extends StatelessWidget {
  const ProUpgradePaywall({
    required this.annualPrice,
    required this.monthlyPrice,
    super.key,
  });

  final String annualPrice;
  final String monthlyPrice;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            const Text('Go Pro'),
            FilledButton(
              onPressed: paywallEvent('continue', args: {'plan': 'annual'}),
              child: Text('Annual, $annualPrice'),
            ),
            OutlinedButton(
              onPressed: paywallEvent('continue', args: {'plan': 'monthly'}),
              child: Text('Monthly, $monthlyPrice'),
            ),
            TextButton(
              onPressed: paywallEvent('restore_purchases'),
              child: const Text('Restore purchases'),
            ),
          ],
        ),
      ),
    );
  }
}
```

The two prices are constructor parameters. Your app passes them in when it renders the paywall, as [host data](/authoring/host-data). Each button sends an event with a name you pick and, optionally, a map of values.

You can pick any event name except these:

- `purchase` and `restore`
- The SDK's own `restage.purchase…` and `restage.restore…` names
- `__restage_measurement_tap_v1`

Use something like `restore_purchases` instead.

A paywall can also declare its events as `SurfaceEvent` constants and fire them with `surfaceEvent`, like a flow screen does. Your app gets the same `PaywallCustomEvent`, with the value under `args['value']`.

## Complete a paywall

`@Paywall(completesOn: [...])` lists the events that count as a completed paywall in analytics, such as starting a trial. A tap fires one with `paywallEvent('start_trial')` or `surfaceEvent(ProUpgradePaywall.startTrial)`. That works in the callback of a built-in widget or your own widget, including inside a wrapper. The build stops if no tap fires one of the listed events.

If a parent `GestureDetector` should get the tap instead of a child that has its own, wrap the child in `IgnorePointer` and set `behavior: HitTestBehavior.opaque` on the detector. That's how Flutter works too. Without `opaque`, the detector only gets taps its child gets. An ignored child loses them.

Run the build:

```sh
dart run build_runner build
```

To let users tap a plan to select it before they continue, see [Interactive surfaces](/authoring/interactive-surfaces) and the [minimal paywall starter](/starters).

## Mount it

Import the file you wrote and mount `ProUpgradePaywallSurface`. Pass the prices and an event handler. The mount keeps your compiled widget as its fallback, and that's why it works offline without a bundle.

```dart
ProUpgradePaywallSurface(
  annualPrice: annualPriceLabel,
  monthlyPrice: monthlyPriceLabel,
  onEvent: (event) {
    switch (event) {
      case PaywallCustomEvent(eventName: 'continue', :final args):
        startPurchase(args['plan'] as String);
      case PaywallCustomEvent(eventName: 'restore_purchases'):
        restorePurchases();
      case _:
        break;
    }
  },
)
```

`startPurchase` and `restorePurchases` stand for your app's own purchase code. `RestagePaywall` renders the paywall with your registered Flutter widgets and your app's current theme.

If delivery isn't available, the mount shows your compiled widget. See [generated fallback mounts](/delivery/hosted-delivery#generated-paywall-and-flow-mounts).

A direct `RestagePaywall(id: ...)` mount needs widget registration and a fallback, such as bundled content or `fallbackBuilder`. See [Bundled assets](/delivery/bundled-assets).

## The onEvent callback

`onEvent` is where your app reacts to the paywall. Events are typed, and you match the ones you care about and ignore the rest:

- `PaywallViewed` fires when the paywall is shown. It carries the published version if the paywall came from a server.
- `PaywallDismissed` fires when the paywall closes. It has the reason and how long the user spent on it.
- `PaywallLoadStarted`, `PaywallLoadCompleted` and `PaywallLoadFailed` report loading.
- `PaywallCustomEvent` carries an event the paywall sent, with the name and values you wrote. Your app decides what to do with it, like starting a purchase, opening the terms or pushing a screen.

The build stops with an error if a surface uses a reserved event name or calls the older `paywallPurchase` and `paywallPriceFor` helpers.

## Multi-screen paywalls

A paywall can have more than one screen. If you already open the next screen with `Navigator` in one of the forms below, the build converts it into a flow. Mount the entry paywall's generated widget. You don't need a `@FlowGraph`. The [examples app](https://github.com/restage-dev/restage/tree/main/apps/examples) has an entry paywall that opens a second "choose a plan" screen.

The build converts a push when:

- An `onPressed` or `onTap` callback makes one synchronous `Navigator.push(context, route)` or `Navigator.of(context).push(route)` call. Use the `build` method's `context` directly.
- The route is an inline `MaterialPageRoute` or `CupertinoPageRoute`, and you pass only `builder`.
- The builder constructs a `@Paywall()` destination with its unnamed constructor and no arguments.

The pushed paywall can return with `Navigator.pop(context)`. Pushes go one level deep, and the destination can't push another paywall. The entry paywall needs a dismissal event, such as `paywallEvent('skip')`.

The conversion doesn't cover awaited navigation, reading a route result, `pop` with a result, or root-navigator overrides. Navigation the conversion doesn't cover still works. A call like `Navigator.of(context).maybePop()` becomes an action, and other navigation renders from your app. You can also handle it in the mount's event handler. For branching, host actions or results, write an explicit [flow definition](/flows/overview).

An automatic paywall flow is the one case that needs a bundle. Hosted delivery checks published versions against the bundled copy, and without it the mount runs your compiled widget. Other generated paywall mounts and explicit flow mounts don't need bundles. See [Hosted delivery](/delivery/hosted-delivery#generated-paywall-and-flow-mounts).

## Paywalls in an explicit flow

A paywall can also be one step in an onboarding, message, survey or general flow:

```dart
@FlowGraph(id: 'message_offer', surface: Surface.message)
const messageOffer = FlowDefinition(
  start: MessageNotice,
  transitions: [
    Transition(MessageNotice.openOffer, to: UpgradeOffer),
    Transition.complete(UpgradeOffer.continueFlow),
  ],
);
```

`MessageNotice` is a `@Screen` and `UpgradeOffer` is a `@Paywall`. Each declares its events as `SurfaceEvent` constants, like `static const continueFlow = SurfaceEvent<Map<String, Object?>>('continue')`.

Mount the flow with the generated `MessageOfferSurface`. The flow owns its events and transitions, and a [host action](/flows/host-actions) covers waiting on purchase work. The purchase adapters for standalone paywalls use different events.

The build records single-screen and multi-screen paywalls in the same publication manifest. Pushing and rolling back work the same for both. Generated mounts keep your compiled widgets as the fallback.
