`restage_codegen` turns your `@RestageWidget` widgets and `@Screen` screens into an A2UI
catalog for Google's [`a2ui_flutter`](https://pub.dev/packages/a2ui_flutter) renderer.
A generative-UI model can then build screens from your widgets.

The catalog describes your own widget classes only. Flutter, Material, Cupertino and
Restage built-in widgets aren't copied into it.

You annotate your widgets, generate the catalog and connect it to A2UI in your app. None of that needs a Restage upload or a publish, and `restage build push` is only for dashboard previews. Restage doesn't fetch, host or stream A2UI payloads. Your app or your model session does.

## Add the dependencies

```yaml
dependencies:
  a2ui_flutter: 0.0.1-wip003
  a2ui_core: ^0.4.0
  json_schema_builder: ^0.1.7
  restage_a2ui:
    path: ../restage_a2ui
  rfw_catalog_schema: ^2.0.0

dev_dependencies:
  build_runner: ">=2.4.0 <3.0.0"
  restage_codegen:
    path: ../restage_codegen
```

`a2ui_flutter` renders the payloads. The generated catalog imports `restage_a2ui`, the package that also provides the pre-render check described below. The code generator runs at build time
and doesn't ship in your app.

## Turn on the A2UI builder

The A2UI builder is off by default because its generated Dart imports `a2ui_flutter`. Add
a `build.yaml` to the package that declares your widgets:

```yaml
targets:
  $default:
    builders:
      restage_codegen:user_a2ui_catalog:
        enabled: true
```

This doesn't need RFW bundling. Leave `bundled_runtime` at its default, `false`, and don't add any generated surface assets to the app.

Keep the other Restage builders on if the app also delivers Restage surfaces. In an
A2UI-only package you can turn them off, like the
[`restage_a2ui` example](https://github.com/restage-dev/restage/tree/main/packages/restage_a2ui/example)
does.

Each widget library in the catalog needs a `@RestageLibrary(capabilityVersion:)`
declaration. Raise the version when you add a widget or change how one renders.
[Custom widgets](/authoring/custom-widgets#3-declare-exact-library-ownership) shows the
barrel file.

## Describe components for the model

Document every catalog component and every public input with Dartdoc, including screen
inputs. The model reads it as the schema description, and for inputs `@RestageProperty(description: ...)` works too.

Two more annotations shape what the model sees:

- `@a2ui.Config.usage('…')` tells the model when to pick the widget. It becomes the widget's line in the catalog's system prompt, and without it the description is used.
- `@a2ui.Config.writeBackValue('propertyName')` names the value a callback writes back
  when that isn't obvious.

A value property paired with a `ValueChanged` callback of the same type becomes a two-way
binding.

[Custom widgets](/authoring/custom-widgets#4-add-useful-target-specific-configuration)
and [Write a surface](/authoring/write-a-surface#one-source-three-targets) have full
examples that compile in the public example package.

A standalone `@Screen(surface: ...)` becomes one component named after its id. The
generated builder constructs your real screen and passes its `SurfaceEvent` calls through.
The screen's widget tree isn't split into A2UI components. A bare `@Screen()` used inside
a flow can also become a component. `@FlowGraph` and `@Paywall` aren't part of the A2UI
catalog. The generator finds all of these anywhere in the package.

Properties can be nested data classes, lists of objects, string-keyed maps, named
records, enums and scalar lists. The generator describes them in the schema and rebuilds
the Dart values in the generated builder. Sealed-class unions aren't supported yet.

If a required property is unsupported, the build stops. You can leave an optional
unsupported property out only when leaving it out gives the same result as its default.

## The payload shape

Each component has an A2UI `id` and `component`. Its constructor inputs are top-level
properties named `props_<DartName>`:

```json
{
  "id": "showcase",
  "component": "CatalogShowcase",
  "props_title": "Catalog proof",
  "props_status": "ready",
  "props_hero": "hero_component_id",
  "props_details": ["detail_a_id", "detail_b_id"],
  "props_footer": "footer_component_id",
  "props_data": {"note": "Generated once", "count": 2}
}
```

A constructor name becomes `props_<DartName>` when it's a valid upstream UAX31
identifier and doesn't start with `encoded_`. Any other name becomes
`props_encoded_<hex>`. That covers `$value` and every name that starts with `encoded_`.
The hex is the name's UTF-16 code units, each written as exactly four lowercase digits.
`$value` becomes `props_encoded_002400760061006c00750065`. Reserving `encoded_` keeps a
normal name from colliding with an encoded one.

Use the property keys from the generated catalog schema and instructions when you produce
payloads. Dart constructor arguments and nested rich-data keys keep their original names.
A nested rich-data key that starts with `@` is written as `@@` on the wire, and the
runtime unescapes it.

Single and list children can use any input name you wrote. A constructor input named
`props` becomes `props_props`.

## Generate the catalog

Run:

```sh
dart run build_runner build
```

The build writes two files:

- `lib/generated/restage_a2ui_catalog.g.dart` has `buildRestageCatalog()`, returning the a2ui_flutter `CatalogImplementation`. The file also has `restageA2uiCapability`, a record of
  what that catalog provides.
- `.restage/build/a2ui/restage_a2ui_catalog.a2ui.json` is a standard A2UI catalog
  document with each component's schema. Give it to whatever produces payloads, like your
  model prompt or your server.

Keep the generated `restageA2uiCatalogId` with that exact catalog. The payload producer
must use it in `createSurface` messages. To combine `buildRestageCatalogItems()` with
another catalog, give the combined catalog a new id of your own and give that catalog to
the producer.

## Connect A2UI and check cached bundles

Use the same catalog for the check and the processor:

```dart
final check = RestageA2uiPreRenderCheck(
  catalogs: [catalog],
  installed: restageA2uiCapability.installedCapability,
  validationConfig: ValidationConfig.strict,
);
final processor = MessageProcessor<ComponentImplementation>(
  catalogs: [catalog],
  defaultVersion: A2uiProtocolVersion.v1_0,
  validationConfig: ValidationConfig.strict,
);
```

Check the complete bundle before you unwrap a Restage sidecar, then pass its payload to `processor.processMessages`. After the surface exists, mount
`A2uiSurface(surface: processor.model.getSurface(surfaceId)!)`. Dispose the processor
along with whatever owns it. Handle renderer errors and keep a native fallback available.

A complete first message looks like this:

```dart
{
  'version': 'v1.0',
  'createSurface': {
    'surfaceId': 'example',
    'catalogId': restageA2uiCatalogId,
    'components': [
      {'id': 'root', 'component': 'BareCatalogCard', 'props_label': 'Hello from A2UI'},
    ],
  },
}
```

The check validates message envelopes, catalog resolution and component schemas. It never
calls functions. For Restage sidecars it also requires the installed library and version
capability set.

Give it the same `validationConfig` as the processor. It applies that config to each
message the way the processor does. It also rejects a finished bundle that has no surface,
an empty surface, a missing root, a dangling reference or a cycle. Catalog ids route
schemas. They don't grant capabilities.

Give the producer the standard catalog JSON and its `instructions`. Your app owns the
model connection and the `onAction` transport. A catalog doesn't start an agent session or
register itself with a remote server.

## Migrating an existing integration

Regenerate the catalog, then update your producers and cached documents to match. Inputs
now use the generated top-level property names. Ordinary names keep `props_<DartName>`.
`props` becomes `props_props` and `id` becomes `props_id`. A name that fails upstream
UAX31 validation, or starts with `encoded_`, uses the UTF-16 hex encoding described
above. Read the regenerated schema when you update producers and cached inputs.

Leave these alone:

- Nested business-data keys.
- Protocol `id`, `component` and `catalogId`. They stay separate from inputs.
- `updateDataModel.path` and child-template `path` fields.

Dynamic references look like `{"@path":"/answer"}` and `{"@call":"functionName"}`.

After you update the repository packages, run `dart fix --apply`. The fix rewrites
`RestageA2uiPreRenderCheck(catalog: expression)` as
`RestageA2uiPreRenderCheck(catalogs: [expression])`. It doesn't regenerate catalogs or migrate a handwritten GenUI host, transport, prompt or cached payload.
Replace those host APIs yourself with `MessageProcessor` and `A2uiSurface`, and give your
producer the standard catalog JSON and its `instructions`. Restage doesn't start or run
an agent service.

Code that read the removed public `.catalog` field has to pick one from `.catalogs`. For
example, use `.catalogs.single` when exactly one is registered. The fix doesn't pick a
catalog for a host with several.

`buildRestageCatalog()` supplies component schemas, instructions and rich catalog-level
definitions. If you compose a `CatalogImplementation` by hand, merge **both**
`buildRestageCatalogItems()` and `buildRestageCatalogDefinitions()`. Keep the
instructions you need, and give a changed set of schemas or components a new catalog id
that your app owns.

### Names and ids

Component type names must be valid upstream UAX31 identifiers and can't be `Surface`. Use
`@RestageWidget(name: ...)` to pick a valid name for a widget.

Native screens use the exact `@Screen(id: ...)` or `@ScreenSource(id: ...)` as their
component type name. Fix invalid ids and everything that uses them yourself. The
generator never silently aliases them.

Component instance `id` values must also be UAX31 identifiers. Update producers and
cached payloads together. Rename each instance id and every child and template reference
to it. For example, rename `callout-body` to `callout_body` in the component declaration
and in every reference. The `Surface` reservation applies only to component type names.
Instance ids and their references are never aliased automatically.

### Write-back paths

A controlled value with an explicit path keeps that path. For a literal or call, the
write-back value is stored locally at
`/restage_<URI-encoded component ID>/<generated property name>`. Inside a template, a `context_<URI-encoded data path>` segment goes before the property name, and each row keeps its own value. This is internal fallback storage, and it isn't the component's identity.
Interaction tests check data-model bindings, local overrides, rebinding and disposal
against the published renderer.

See the [repository package README](https://github.com/restage-dev/restage/tree/main/packages/restage_a2ui)
for the full host example and the interaction tests.
